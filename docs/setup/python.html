1 · Open a terminal

A terminal is a window in which you type the name of a program and it runs. That is the whole idea. It looks unfriendly because it gives no hints, not because it is doing anything complicated.

Press Cmd + Space, type Terminal, press Enter. A window opens with a line ending in % or $. That is the prompt: it means the terminal is waiting for you.

Press the Windows key, type PowerShell, press Enter. A window opens with a line ending in >. That is the prompt: it means the terminal is waiting for you.

Use PowerShell, not the older Command Prompt, and not WSL. Everything on this site is written for PowerShell on Windows.

Throughout the site, terminal blocks look like this. The $ $ at the start is the prompt and is not part of what you type; the copy button strips it for you.

$ python3 --version

Blocks on a grey background, like the one below, are output — what you should see back. Never type those.

Python 3.11.9

2 · Check your Python

Run the command above. You need 3.9 or higher; anything from 3.9 to 3.13 is fine and the exact number does not matter beyond that. If the command is not found, try:

$ python --version

If neither works, install from python.org. On Windows, tick the "Add Python to PATH" box on the first screen of the installer. If you miss it, the terminal will not find Python afterwards and the fix is to run the installer again.

python vs python3, and pip vs pip3

Many machines have two Pythons on them: an old one that came with the operating system, and a newer one you installed. Historically python meant the old one and python3 meant the new one, and on a lot of machines that is still true.

Everything on this site is written with python3 and pip3. If those are not found on your machine, use python and pip instead — consistently, both of them, every time. The failure that costs an afternoon is mixing them: installing a package with pip3 and then running your script with python, which is a different Python that cannot see it. You get ModuleNotFoundError: No module named 'pandas' immediately after a successful install, which is a genuinely confusing thing to be told.

The bulletproof form, if you ever doubt it, ties the two together explicitly: python3 -m pip install -r requirements.txt. That says "use the pip belonging to this Python", so they cannot disagree.

3 · Get the repository

The project lives in a Git repository. Git is worth learning and gets its own page later; for now you need one command. The URL is in the project email.

$ git clone <repo-url>
$ cd SenSym-misconception-aware-llm

Check you are in the right place:

$ lsdir
Makefile authoring docs python pyproject.toml requirements.txt

If you see python and requirements.txt, you are in the repository root, which is where the next command has to run from. If you see something else you are in the wrong folder, and every error after this point will be a file-not-found error that has nothing to do with your code.

The trick for typing paths, which you should never do by hand

Type cd — with a trailing space — then drag the folder from a Finder window onto the Terminal window. The full path appears, correctly quoted and correctly spelled. Press Enter.

In File Explorer, hold Shift, right-click the folder, and choose Copy as path. Then type cd in PowerShell and paste. The quotes come with it, which matters if any folder in the path has a space in its name.

Typing a long path by hand is how you spend twenty minutes debugging a capital letter.

4 · Install the four packages

From the repository root:

$ pip3 install -r requirements.txt

That reads requirements.txt and installs four libraries. If you get a permissions error, add --user: pip3 install --user -r requirements.txt.

PackageWhat it is doing in this project
pandasTables. It reads data/responses.csv, keeps the forty rows with their labels and the model's predictions side by side, and writes results/metrics.csv back out.
requestsHTTP. One function call per response, sending a prompt to the local model at localhost:11434 and getting text back. Not needed at all in mock mode.
matplotlibCharts. It draws confusion_matrices.png and comparison.png, the two figures that go in your write-up.
scikit-learnA second opinion. It computes the confusion matrix and the metrics independently, so your version can be checked against it. See below — this one is not what it looks like.

Why a machine-learning library is here when you are not doing machine learning

Reasonable question, and the answer is the interesting part of this section. scikit-learn is not doing the analysis. It is marking the analysis.

In Phase 2 you write the four counts of the confusion matrix yourself, by hand, in compute_confusion(). Those four numbers are the entire study: every metric in your results is arithmetic on them, with M — "this response contains a misconception" — as the positive class.

$$\text{precision} = \frac{TP}{TP + FP}, \qquad \text{recall} = \frac{TP}{TP + FN}$$

If one of those four counts is wrong, every number downstream is wrong, the charts are wrong, and nothing about the output looks unusual. That is the dangerous kind of bug: it does not crash, it just lies quietly.

So the project computes the same thing twice, two different ways, and insists they agree. analyze.py prints the comparison on every run:

=== baseline === TP=4 FP=4 FN=2 TN=2 (unparseable: 0) accuracy=0.5 precision=0.5 recall=0.667 f1=0.571 scikit-learn cross-check: MATCH ✓ sklearn precision=0.500 recall=0.667 (yours: 0.500 / 0.667)

And the test suite does it again, more strictly. test_confusion_agrees_with_sklearn builds a small table whose answer is known by construction — seven true positives, three false negatives, two false positives, eight true negatives — runs your compute_confusion() over it, runs sklearn.metrics.confusion_matrix over it, and asserts the two results are identical. A separate test does the metrics by hand on paper first (accuracy = (8+6)/20 = 0.7) and asserts the code produces that.

The habit worth stealing from this, whatever you do later

Whenever you implement something yourself, check it against an implementation that is already trusted. Not instead of writing it — the writing is where the understanding comes from — but alongside it. When they disagree, it is almost always you, and you find out in two seconds instead of finding out from a wrong number in a paper.

This is why "just use the library" is the wrong instinct here and "only use my own code" is also the wrong instinct. You want both, and you want them to argue.

Nothing is broken; they're just steps you haven't reached.

That output is a pass. Read the last block again: three things are unfinished and the script still says your environment is working, because those two statements are about different things.

The three markers · confusing two of these wastes days

[OK] — this is present and working. Nothing to do.

[TODO] — you have not got there yet. Nothing is broken. Your two data files are still the blank template, and Ollama is not installed, and on a fresh clone that is exactly the correct state of the world. These lines are a map of what is ahead, not a list of faults. There are three of them at the start of the project and there will be none at the end.

[FIX] — something is genuinely broken and will stop you. A missing package, a Python older than 3.9, a CSV the code could not read at all. Each one prints an indented -> line telling you the command that repairs it.

The summary line tells you which kind you have. ✓ Your environment is working means there were no [FIX] lines at all. ✗ N thing(s) are genuinely broken means there were, and it is the only sentence on the page you have to act on today.

The distinction exists because both failures feel identical when you are new: something is red, so something is wrong, so you stop. Weeks get lost to a student trying to make a [TODO] go away in week one, and to a student ignoring a [FIX] because they assumed it was one of the expected ones. The script separates them for you so you never have to guess. observed — this is the single most common way this stage goes wrong, in my experience of running it, not a measured claim.

6 · The ninety-second proof

Now run the entire study. Both conditions, all the analysis, both charts:

$ python3 misconception/run_experiment.py --mock --sample
$ python3 misconception/analyze.py

--mock swaps the real model for a fake one that answers instantly and needs nothing installed. --sample swaps your empty data files for the twelve demo responses in python/data/sample/. Together they mean a repository you cloned four minutes ago runs end to end. Here is the first half:

*** MOCK MODE — these numbers are FAKE. Never report them. *** *** SAMPLE DATA — 12 demo answers, NOT yours. *** Loaded 12 answers (6 misconception, 6 correct) Loaded 3 misconceptions --- Condition: baseline --- ..XX.X..X.XX Done in 0.0s (0.0s per item) Saved -> .../python/results/predictions_baseline.csv

Each . is an item where the model agreed with the label and each X is one where it did not, printed live so you can see it has not frozen. In mock mode the whole thing takes a fraction of a second. In Phase 4, with the real model, that same row of dots takes several minutes and is the only way to tell the run apart from a hung terminal.

The reference fallback, which is the most important thing on this page

At the end of the run you get this:

──────────────────────────────────────────────────────────────────────── ⚠ 2 TODO(s) not done — the worked versions were used. The numbers above are real, but they aren't YOUR code's numbers yet. ──────────────────────────────────────────────────────────────────────── TODO 4a misconception/run_experiment.py · run_condition() → build the prompt with build_prompt(...) TODO 4b misconception/run_experiment.py · run_condition() → send the prompt with ask(...)

Here is what happened. There are six places in this project where you have to write a line of code, and each of them is wrapped in a call to todo.pending() in todo.py. That function is handed whatever your line produced. If it is None — which is what the repository ships with — it quietly runs a worked version from reference.py instead, and writes down that it did so. The run completes. The CSVs get written. The charts come out.

So: an unfinished TODO cannot crash this project. It produces a yellow warning naming the file, the function and the one thing that line was supposed to do, and then the program carries on. When all six are yours, the yellow block is replaced by one green line:

✓ Nothing fell back — this run was entirely your code.

The consequence is worth saying as sharply as it can be said, because it is the sentence that will save you the most time on this project. Any crash you see is a real problem. It is never "I have not got there yet." A traceback means a missing package, a wrong folder, a mistyped filename, or a bug in something you changed. It does not mean the TODOs are unfinished, because unfinished TODOs are designed not to be able to do that. If the program stops, stop looking at the checklist and start reading the error.

Two warnings, then four, and it is not a bug

run_experiment.py reports two fallbacks and analyze.py reports four. That is because each script is its own running program, and the list of fallbacks that fired lives inside one program while it runs. run_experiment.py only ever touches TODO 4a and 4b; analyze.py only ever touches TODO 5a to 5d. Two plus four is the six.

The other numbered TODOs on the checklist — reading the baseline prompt, deciding whether the model should see all ten misconceptions or only the relevant one, and writing up what the numbers mean — have no fallback because they are not lines of code. Nobody can run them for you and no warning will remind you.

The second command, analyze.py, reads the two prediction files, counts the four cells, computes the metrics, cross-checks them against scikit-learn, and writes three files into python/results/: metrics.csv, confusion_matrices.png and comparison.png. Open the two images. They are the actual figures your write-up will contain, with the actual axes and the actual layout, five minutes into the project and with none of the work done.

Nothing produced here may be reported

Everything from --mock and everything from --sample is demo data. The twelve responses in python/data/sample/ are examples written to exercise the code; the fake model is a keyword rule with deliberate noise. Their numbers exist to prove the plumbing carries water and for no other reason. Not one of them may appear in your results, your slides or your abstract, even as an illustration.

You will see this warning on every page where a reader could be tempted, which is most of them.

7 · Why the fake model is deliberately bad at its job

Read ask_llm_mock() in llm_client.py. It looks for overconfident words in the response — always, never, impossible, guarantee — and says M if it finds any. Then it does something that looks like sabotage: it computes a number from the length of the text and flips its own answer on roughly thirty per cent of items.

That flip is the point. A mock that answered every item correctly would produce a confusion matrix with two of its four cells empty, and two empty cells means half of compute_confusion() is never exercised, half of the metric formulas are never exercised, and a mistake in either is invisible.

Lab · how accurate should a fake model be

A simplified stand-in for the mock: each of the twelve demo responses is answered correctly if the model's accuracy clears a fixed per-item threshold, so the picture is deterministic and moves smoothly. The four curves are the four cells of the confusion matrix. Shaded columns are settings where at least one cell is empty. Drag towards 100% and watch what a perfect mock would give you. The figure under each metric is its 95% Wilson score interval; on twelve items they are enormous, which is worth seeing once before you meet the same intervals on forty.

The comment in llm_client.py puts the fake model at about seventy per cent accurate. On the twelve demo responses it actually gets six of twelve right observed, which is precisely the majority-class baseline — the score you would get by ignoring the text and always guessing M. That is a useful thing to have seen once: the mock is not a weak model, it is a model with no skill at all, and it still produces a full confusion matrix, four metrics and two charts that look entirely respectable. Numbers can be well-formed and mean nothing. This is why the run shouts these numbers are FAKE at you twice before it does anything.

8 · Run the tests

From the repository root:

$ cd ..
$ pytest -q
................... [100%]

Nineteen dots, one per test, and no letters. A test is a small program that checks another program still does what it did yesterday. These nineteen check the metric arithmetic against hand-worked answers, the four confusion-matrix counts against scikit-learn, the verdict parser against six awkward replies, the two prompts against the property that makes the comparison fair, the fallback machinery itself, and finally the whole pipeline end to end by running the two scripts exactly as you just ran them and confirming all five output files appear.

You are not asked to write any tests. You are asked to run them after every change you make, because the alternative to finding out in two seconds is finding out from a wrong number in your results.

What a failure looks like, so it is not alarming later

A failing test prints F instead of ., then the name of the test, then the line that failed and both values it compared. That is a complete diagnosis: the test names what was expected, and pytest shows what it got instead. Read those two numbers before changing anything.

All nineteen pass on a fresh clone, before you have written a line, because the reference implementations are behind every TODO. So a failure means you broke something — which is exactly the signal you want a test suite to send.

9 · Exercises

Exercise 1.1 ★★thinking

A fresh clone on a laptop running Python 3.11. The pip3 install was interrupted partway: pandas, requests and scikit-learn installed, matplotlib did not. Ollama has never been installed. Neither data file has been touched.

Write down, line by line, what python3 misconception/check_setup.py prints — the marker on each line, in order, and both summary blocks at the bottom. Then say which single line you should act on today, and why the others can wait.

Solution

The script checks Python, then the four packages in the order they appear in its list, then the two data files, then Ollama:

[OK] Python 3.11 (need 3.9+) [OK] package: pandas [OK] package: requests [FIX] package: matplotlib -> pip install matplotlib [OK] package: scikit-learn [TODO] data/misconceptions.csv — 0 real row(s) [TODO] data/responses.csv — 0 real row(s) [TODO] Ollama is running

and then both summaries, because there is one of each kind:

✗ 1 thing(s) are genuinely broken (marked [FIX] above). Fix those before going further. 3 thing(s) not done yet (marked [TODO]) — all expected on a fresh clone. Nothing is broken; they're just steps you haven't reached.

Three details worth noticing. First, scikit-learn is still [OK]: the packages are checked independently, so one failure does not stop the ones after it. Second, the data-file section still runs, because it imports config and pandas and has no need of matplotlib. Third, the hint line says pip install matplotlib, without the 3 — if pip3 is what works on your machine, use that.

Act on the matplotlib line and nothing else. The two data files are Phase 3 and Ollama is Setup 2; neither is a fault. But the [FIX] would produce a genuinely confusing half-working state if you ignored it: run_experiment.py does not import matplotlib and would run perfectly, while analyze.py imports it at the top and would die immediately. "The first half works and the second half does not" is a much harder thing to diagnose an hour later than it is to read off this list now, which is the entire argument for running check_setup.py first.

Exercise 1.2 ★by hand

pip3 install -r requirements.txt ended with Successfully installed pandas-2.2.2 ... and no errors. The very next command, python misconception/check_setup.py, dies with ModuleNotFoundError: No module named 'pandas'.

What has happened, and what is the one command that both fixes it and prevents it happening again?

Solution

There are two Pythons on the machine. pip3 installed pandas into the newer one; python is the older one, and it has its own separate collection of packages, which does not include pandas. Both commands did exactly what they were asked. Nothing is corrupted and reinstalling will not help.

The fix and the prevention are the same command:

$ python -m pip install -r requirements.txt

-m pip means "run the pip that belongs to this Python". By naming the interpreter once at the front, you make it impossible for the installing Python and the running Python to be different. Then keep using that same word — python or python3, whichever one you just used — for every command on this site.

Worth recognising the shape of this bug rather than just the fix: the error was not about pandas at all. It was about which of two programs you were talking to. The Ollama page has the same lesson in a different costume, where "could not reach the model" turns out to be about which layer you are in rather than about your code.

Exercise 1.3 ★★thinking

Mock mode comes before real mode everywhere in this project. Give two separate arguments for that ordering: one about time, with an arithmetic estimate, and one that is not about time at all and is the more important of the two.

Then describe the one thing mock mode cannot tell you.

Solution

The time argument. The real study is forty responses under two conditions, so eighty calls to the model. At roughly three seconds a call on a normal laptop observed, one full run is about four minutes. Mock mode runs the same pipeline in well under a second. If it takes ten attempts to get compute_confusion() right — which is a realistic number for code you are writing for the first time — that is forty minutes of watching a progress bar against a few seconds. And the forty minutes are not spent learning anything.

The better argument: isolating the variable. If you debug your code and your model install at the same time, every failure has two candidate causes and you cannot tell them apart. Mock mode removes the model from the system entirely — no HTTP, no server, no download, no requests — so any failure that remains is definitely yours. When you later switch on the real model, your code is already known-good, so any new failure is definitely the model or the install. Each step has exactly one thing that can be wrong. That is the same instinct as the experiment itself: the baseline and misconception-aware conditions differ in the prompt and in nothing else, because a comparison in which two things changed tells you nothing about either.

What mock mode cannot tell you. Anything about the actual research question. The fake model ignores which prompt it was given, so the two conditions come out byte-for-byte identical — you can see it in the output above, where both print TP=4 FP=4 FN=2 TN=2. That is expected, not a bug: there is no real model there for the prompt to influence. Mock mode proves the pipeline carries water. It cannot say anything whatsoever about whether the misconception catalogue helps, and a difference between conditions is the one thing you must never look for in it.

Exercise 1.4 ★★thinking

On a fresh clone, run_experiment.py --mock --sample reports two fallbacks and analyze.py reports four.

(a) Why two and four rather than six and six? (b) You then complete TODO 4a and rerun both scripts. Exactly what changes in each of the two outputs? (c) What would you have to do to see the green line from analyze.py but still see a yellow block from run_experiment.py?

Solution

(a) The record of which fallbacks fired lives in a list inside todo.py, and that list exists only while a program is running. Each script is a separate program with its own fresh copy. run_experiment.py only ever calls todo.pending() for TODO 4a and 4b, in the loop in run_condition(); analyze.py only ever calls it for TODO 5a to 5d, in compute_confusion(). Neither script can report on the other's TODOs because neither script executes the other's code. Two plus four is the six.

(b) run_experiment.py now reports one fallback instead of two: TODO 4b, with the same file and function and the note send the prompt with ask(...). analyze.py is unchanged and still reports four. It reads prediction CSVs off the disk and does not care who built the prompts that produced them.

(c) Finish all four of TODO 5a to 5d and leave either 4a or 4b unfinished. Then analyze.py prints ✓ Nothing fell back — this run was entirely your code while run_experiment.py still prints yellow. This is not a trick: the two halves of the project are genuinely independent, and the green line from one script is a statement about that script only. The finish line for Phase 2 is green from both.

Exercise 1.5 ★★arithmetic

In Phase 2 you write the four counts. A very common first attempt writes the true positives with | instead of &:

tp = len(scored[(scored["ground_truth"] == M) | (scored["prediction"] == M)])

The other three lines are correct. Run on the demo data, whose true counts are TP=4, FN=2, FP=4, TN=2 over twelve scored items: what number does that line produce, what does the program do next, and is this a crash you should worry about?

Solution

| means "or", so instead of counting the rows where the truth is M and the prediction is M, that line counts every row where the truth is M or the prediction is M. Three of the four cells satisfy that: the true positives (both are M), the false negatives (the truth is M) and the false positives (the prediction is M). Only the true negatives are excluded.

$$tp_{\text{wrong}} = TP + FN + FP = 4 + 2 + 4 = 10$$

The other three lines are right, so the four numbers are now 10, 2, 4, 2 and they sum to 18. compute_confusion() checks that sum against the number of scored items:

Your four counts add up to 18, but there are 12 scored items. -> One of the conditions in TODO 5 is wrong. Check that you used & (and) not | (or), and that each row lands in exactly one box.

and stops. Yes, worry about it — and that is the correct response. This is a stop, not a fallback, which by the rule on this page means it is a real problem in your code rather than something unfinished. The guard exists because every row of the data belongs in exactly one of the four boxes, so the four counts must sum to the number of rows. Any arithmetic that breaks that identity is wrong, whatever else it looks like, and catching it here is much cheaper than noticing a strange recall three weeks later.

Note what the guard does not catch: any error that leaves the total intact. See the next exercise.

Exercise 1.6 ★★thinking

Now suppose you swap TODO 5b and 5c: your fn line counts the rows where the truth is C and the prediction is M, and your fp line counts the rows where the truth is M and the prediction is C. Everything else is right.

(a) Does the sum check from the last exercise catch it? (b) Does the scikit-learn cross-check in analyze.py catch it? (c) Of the two confusion-matrix tests in the suite, which one catches it, and why does the other one fail to?

Solution

(a) No. Each row still lands in exactly one box; two of the boxes have simply exchanged labels. On the demo data you get TP=4, FN=4, FP=2, TN=2, which still sums to 12. The guard is silent. Meanwhile recall has gone from 4/(4+2) = 0.667 to 4/(4+4) = 0.5 and precision has gone the other way, so the headline number of the entire study is wrong and nothing has complained.

(b) Yes. cross_check_with_sklearn() compares your four counts against sklearn.metrics.confusion_matrix as a tuple, so it notices as soon as your FN and your FP differ from each other. On the demo data they do — 4 against 2 — and the line prints MISMATCH ✗ — recheck TODO 5. This is exactly the case the second opinion is there for: an error that produces plausible, well-formed, entirely wrong numbers.

(c) test_confusion_agrees_with_sklearn catches it. It uses a table with seven true positives, three false negatives, two false positives and eight true negatives; three does not equal two, so the swap changes the answer and the assertion fails.

test_confusion_counts_land_in_the_right_boxes does not catch it. Its little six-row table has one false negative and one false positive, and swapping two equal numbers changes nothing at all. The test passes on broken code.

This is the lab's point arriving in a second costume. A test whose false negatives and false positives happen to be equal is blind to any confusion between them, in exactly the way a mock model that never makes a mistake is blind to both. If you want a check to be able to fail, the case you feed it has to be asymmetric enough that a wrong answer looks different from a right one.

Exercise 1.7 ★★★writing

Someone reads your repository and asks a sharp question: "You import scikit-learn, which computes confusion matrices in one line. Why is there a hand-written version at all? Either the library is right and yours is redundant, or yours is right and the library is redundant."

Answer in a short paragraph you would be happy to say out loud. Include the arithmetic from test_metrics_match_hand_calculation as your worked example.

Solution

The question assumes the two versions are doing the same job. They are not.

The hand-written version exists because I have to be able to say what the numbers mean, not just produce them. The test suite pins that down with a table I can work through on paper. Take TP = 8, FP = 2, FN = 4, TN = 6, twenty items in total, with M — "contains a misconception" — as the positive class:

$$\text{accuracy} = \frac{8+6}{20} = 0.700, \qquad \text{precision} = \frac{8}{8+2} = 0.800, \qquad \text{recall} = \frac{8}{8+4} \approx 0.667$$

$$F_1 = \frac{2 \times 0.800 \times 0.667}{0.800 + 0.667} \approx 0.727$$

Every one of those is arithmetic I can do without a computer, and each has a sentence in English attached to it: of the twelve responses that really did contain a misconception, the model caught eight, so recall is two-thirds. If I could only get that from a library call I would not be able to defend the result, spot an implausible one, or notice that a denominator had gone to zero.

scikit-learn exists for a different reason: it is a second, independently written implementation, so agreement between the two is evidence that my arithmetic is right. It is not redundant, because it is not the same claim. Mine says I know what a false negative is. The cross-check says and I counted them correctly. Those fail separately and both matter, so the project runs both on every analysis and the test suite asserts they agree.

The honest limit of the argument: agreement only shows the two implementations match. If I fed both of them the wrong column, or labelled twenty responses badly in Phase 3, they would agree beautifully on a meaningless answer. Cross-checking protects the arithmetic. It cannot protect the data, which is why Phase 3 has a second reader rather than a second library.

Going deeper (optional)

There is a Makefile in the repository root, which is a list of shortcuts for the commands on this page. If make exists on your machine:

$ make help
$ make check
$ make demo

make demo is exactly the two commands from section 6, and make help prints every shortcut with a one-line description. Windows usually does not have make; nothing is lost, because you can read the recipe for any target straight out of the file and paste the command in yourself. That is a good reason to open the file once: a Makefile is a readable list of the real commands, and reading one is a fast way to learn what a project actually does.

The other file worth opening early is python/misconception/config.py. Every setting in the study lives in it — the model name, the temperature, the two condition names, and the choice of M as the positive class, each with a comment explaining why. When somebody asks "which model, at what temperature?", and somebody will, the answer is in one file rather than scattered across five scripts. Design your own projects this way.
