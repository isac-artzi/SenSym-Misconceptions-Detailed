The setup track: what order, and why

Four short pages, about an hour, most of it spent waiting for downloads.

Setup is where projects like this quietly lose a fortnight, almost always for the same reason: two things are broken at once and there is no way to tell which is which. This page is the orientation. It tells you what order to do the three installs in, what each one buys you, and how to arrange things so that when something fails you already know which layer it failed in.

By the end of this page you can

  • State the order of the setup track and give the reason for it in one sentence.
  • Say what --mock --sample does and why it is the most useful fact here.
  • Name the three layers an error can live in, and sort a real error message into one.
  • Budget your time across the three steps rather than discovering the download at midnight.
  • Say what breaks if you skip any one step, and what does not break.
  • Explain why the dataset — not the install — is the long pole of this project.

1 · The order

Three installs, in this order, and the order is not arbitrary.

Step 1 · first
Python, the repo, and the first run
 Step 2 · second
Ollama and the local model
 Step 3 · last
Git, the small version

The rule behind the ordering is one sentence: get the pipeline provably running on a fake model before you add a real one. Step 1 ends with charts written to python/results/ — real files, produced by the real analysis code — with no model anywhere on your machine. Only then do you install Ollama.

The reason is diagnostic, not aesthetic. Suppose you install everything at once and then run the experiment and it fails. The failure could be in your Python, in the packages, in the Ollama server, in the model name, or in the data files. Five candidates, and testing them requires changing one thing at a time anyway — so you may as well have added them one at a time in the first place. Debugging your code and your model install simultaneously is the trap. Each layer added on its own turns a five-way mystery into a one-way one: the thing that broke is the thing you just changed.

Three layers · learn to name them

The machine layer — is Python there, are the four packages installed, is the repository on disk. Errors look like command not found or ModuleNotFoundError.

The model layer — is Ollama installed, is its server running, is llama3.2:3b downloaded, does the name match the config. Errors mention localhost:11434 or model not found.

The project layer — your code, your prompts, your forty responses. Errors are about columns, labels, counts and unparseable verdicts.

Nearly every hour lost on a project like this is lost because an error from one layer was treated as an error from another. Sorting the message into a layer before touching anything is most of what debugging actually is.

2 · The single most useful fact on this track

Here it is, and it is worth reading twice.

The whole pipeline runs with no Ollama, no model, and no data at all 
$ cd python
$ python3 misconception/run_experiment.py --mock --sample
$ python3 misconception/analyze.py

That produces python/results/metrics.csv, python/results/comparison.png and python/results/confusion_matrices.png in about a second, on a laptop with no language model installed and an empty data/responses.csv.

Two flags are doing the work, and they are independent of each other. --mock replaces the call to the model with a fake one that returns a canned verdict instantly, so nothing touches the network and nothing needs Ollama. --sample reads the twelve demo responses in python/data/sample/ instead of the forty you have not written yet. Together they mean the pipeline is testable from the moment you clone the repository.

And the corresponding rule

Numbers produced by --mock or --sample are demo output. The mock model does not read the response it is judging in any meaningful way, and the twelve sample items were written by somebody else. No number from either goes into your write-up, ever, not even as an illustration. They exist to prove the plumbing works — which is a completely different job from producing a result, and an important one.

This changes what setup is for. Setup is not a gate you must pass before the project starts. Two thirds of the project — the six code TODOs in Phase 2, the forty responses in Phase 3, every chart, and the entire test suite — never need a model at all. If Ollama defeats your laptop for a week, you keep working the whole week.

Five things you have or have not installed, five things the project asks you to do. Start with only Python ticked and add things in the track's order. Notice how many boxes turn green before Ollama is ticked at all — that count is the argument for the order, and the reason step 2 is allowed to be the slow one.

The shape of that picture is the point. Three of the five capabilities are unlocked by Python and four packages — a ten-minute job. The fourth needs the model, and the fifth needs something no installer can give you: forty responses that you wrote and labelled yourself.

4 · The time budget

Roughly an hour in total, and most of that hour is a progress bar rather than you doing anything. Times are observed from setups like this one on ordinary home wifi; a school network can easily double the download row.

Because half of it is waiting, do not sit and watch it. Start the model download at the beginning of step 2 and read the rest of that page — or better, open Phase 3 and start drafting responses — while it runs. The download does not care whether you are looking at it.

The four commands that matter on this track 
$ cd path/to/SenSym-Misconceptions-Detailed/python
$ python3 misconception/check_setup.py
$ python3 misconception/run_experiment.py --mock --sample
$ python3 misconception/analyze.py

Everything on the setup track is in service of getting those to run. The test suite is run from the repository root instead, one level up from python/:

$ pytest -q

check_setup.py is the one to keep rerunning. It prints [OK] for things that work, [TODO] for things that are expected to be unfinished on a fresh clone, and [FIX] for things that are genuinely broken. Only [FIX] is a problem.

5 · What breaks if you skip a step

Skipping is not always wrong — one row of this table is genuinely optional for weeks. The point is to know which one.

If you skipThe first thing that breaksWhat you seeLayer
Python 3.9+ Everything. Nothing in the project runs. command not found: python3 machine
pip install -r requirements.txt Every script, on its import line, before it does any work ModuleNotFoundError: No module named 'pandas' machine
The --mock --sample run Nothing, today. Later: your first real failure has five possible causes instead of one, because nothing was ever known to work. No error — that is exactly the problem —
Installing Ollama, or starting its server Only the real run. Tests, mock runs and charts are untouched. Could not reach Ollama at http://localhost:11434/api/generate model

Git Nothing runs differently. You lose the ability to say which version of the code produced which numbers, and the ability to undo a bad afternoon. No error, and that is why people skip it project
Writing your forty responses The real experiment refuses to start rather than quietly using demo data ERROR: data/responses.csv has no real rows yet. project

Notice the shape of the last column. Two rows produce no error at all. Those are the two that cost the most, because a missing safety net announces itself only at the moment you needed it.

Why Git is last and not first

Most programming courses teach version control on day one. This track puts it third, on purpose: Git is the only step whose absence breaks nothing today, so putting it first spends your patience on the step with the least immediate payoff — and patience is finite on a Tuesday evening.

It is still not optional. By Phase 4 you will have two runs of the same experiment that disagree slightly, and the question "what was different about the code that produced this one?" becomes answerable or unanswerable depending on whether you did step 3. Do it before you start writing data, not after.

6 · Exercises

These are all thinking exercises. None of them needs a computer, and doing them properly before you install anything will save you more time than reading the next page twice.

Exercise 0.1 ★thinking

You run python3 misconception/run_experiment.py --mock --sample and get:

ModuleNotFoundError: No module named 'pandas'

Which layer is this in, and what is the fix? Name one thing you should specifically not do next.

Solution

Machine layer. The message is from Python's import machinery: it looked for a package called pandas and there was no such thing installed. It has nothing to do with the model, the data or your code — the script never got as far as running a single line of its own logic.

The fix is pip install -r requirements.txt from the repository root, which installs pandas, requests, matplotlib and scikit-learn. Then rerun python3 misconception/check_setup.py and confirm all four package lines say [OK].

What not to do: do not go and install Ollama. This is the classic wrong move — the run failed, Ollama is the scary uninstalled thing, so it must be Ollama's fault. It is not, and you can prove it without leaving your chair: the flag you passed was --mock, and mock mode never contacts a model. Sorting the error into a layer first is what stops you from spending an evening on the wrong install.

Exercise 0.2 ★★thinking

A classmate cloning the same repository sends you this:

LLMError: Could not reach Ollama at http://localhost:11434/api/generate

and says "but I ran it with --mock, so it shouldn't need Ollama at all — the website is wrong." Is the website wrong? What actually happened?

Solution

The website is not wrong, and this is a nice piece of reasoning because the conclusion is forced rather than guessed.

In mock mode the code calls ask_llm_mock(), which returns a canned reply and never builds an HTTP request. The connection error is raised inside ask_llm(), which is a different function. So the appearance of this error is proof that the real path ran — that is, the run was not in mock mode, whatever the person believed.

Two likely causes, both worth checking before anything else: the flag was mistyped (-mock with one dash, or --Mock), or the flag was attached to the wrong command — analyze.py does not take --mock, and neither does check_setup.py. Have them paste the exact command line rather than describing it.

The general habit: an error message tells you which code path executed. When the message contradicts what you think you ran, believe the message. This one costs thirty seconds if you reason about it and an hour if you start installing things.

Exercise 0.3 ★★by hand

Here is real check_setup.py output. Say which lines require action, in what order, and which require none.

[OK] Python 3.11 (need 3.9+) [OK] package: pandas [OK] package: requests [FIX] package: matplotlib -> pip install matplotlib [OK] package: scikit-learn [TODO] data/misconceptions.csv — 0 real row(s) [TODO] data/responses.csv — 0 real row(s) [TODO] Ollama is running
Solution

One line requires action: the [FIX]. Run pip install matplotlib — or better, pip install -r requirements.txt, which is the same install plus insurance against a second package having gone missing the same way.

The three [TODO] lines require nothing. They are exactly what a correct fresh clone looks like. The two data files still hold their template placeholder rows because you have not reached Phase 3, and Ollama is not installed because you have not reached step 2. The script separates [TODO] from [FIX] precisely so that a first run does not look like a disaster.

Order matters slightly: fix matplotlib first, because analyze.py imports it and cannot draw the charts without it — so the missing package blocks the mock run that would otherwise be your next move. Then rerun check_setup.py, confirm the line has flipped to [OK], and go straight to --mock --sample.

Reading this output correctly is a small skill with a large payoff: the distinction between "broken" and "not yet reached" is the same distinction the whole setup order is built on.

Exercise 0.4 ★★thinking

It is Tuesday. You have exactly one free hour, and school wifi that will take about forty minutes to pull a 2 GB model. Write down the order you would actually do things in, and justify it in two sentences.

Solution

A defensible plan:

  1. Minutes 0–15. Step 1 completely: Python, the repository, pip install -r requirements.txt, check_setup.py. This is the step everything else depends on and it does not involve a big download.
  2. Minute 15. Install Ollama and start ollama pull llama3.2:3b — then leave it running and stop watching it.
  3. Minutes 15–25, while it downloads. Run run_experiment.py --mock --sample and analyze.py, open the two PNGs in python/results/, and run pytest -q. The download is using the network; these use the processor. They do not compete.
  4. Minutes 25–55. Step 3, Git — also small — and then open Phase 3 and start drafting responses.
  5. Whenever the pull finishes. Rerun check_setup.py and check the two Ollama lines.

The justification: the download is the only step whose duration you cannot influence, so it should be started as early as possible and overlapped with everything that does not depend on it; and because the mock pipeline needs nothing from the model, there is a genuine half hour of useful work available while the bar fills.

If instead you had done the three steps strictly in series with nothing overlapped, the same hour would have ended with a working install and no idea whether the pipeline runs.

Exercise 0.5 ★★thinking

Someone reasonable argues: "The mock model is fake. Testing with it proves nothing about whether the study works, so it is a waste of ten minutes." Answer them — and concede the part of the objection that is correct.

Solution

Concede this much: they are right that mock output carries no scientific information. The mock model does not read the response in any meaningful sense, so the confusion matrix it produces is arithmetic on noise. Any conclusion drawn from those numbers would be worthless, which is why the rule is that they never appear in the write-up.

But the mock run is not testing the study. It is testing everything around the study. Passing it establishes that Python runs, the packages import, the CSV files parse, the prompt builder produces a string, the verdict parser turns a reply into M or C, the results directory is writable, the metric code runs, and matplotlib can save a PNG. That is a long list of things that can be broken, and every one of them would otherwise be discovered later, mixed in with a model that might also be broken.

The measurable payoff is in how many candidate causes a future failure has. After a successful mock run, a failure in the real run has essentially one plausible cause — the model layer, the only thing that changed. Without it, the same failure has five. Ten minutes now to divide your future debugging time by five is an excellent trade.

This is the same logic as the test suite, and the same logic as changing one prompt at a time in Phase 4. It is the habit the whole project is built on.

Exercise 0.6 ★★★writing

Your school laptop refuses to install Ollama and it is not going to be resolved this month. Using the readiness lab above, write three or four sentences to your mentor saying precisely what you can still do, what you cannot, and what you need. Be specific about which phases are affected.

Solution

A good message is short, states the blocked capability rather than the feeling, and arrives with a proposal. Something like:

Ollama will not install on the school laptop — the installer is blocked. Python, the packages and the repository are all fine: check_setup.py is green except the two Ollama lines, and --mock --sample produces the charts in python/results/. So Phase 2 and Phase 3 are unaffected and I am carrying on with the forty responses. The only thing blocked is the one real run in Phase 4, which needs one afternoon on a machine that will take the install — can I use a home computer for that, or should we do it together on a call?

Why this version works. It names the layer (model, not machine or project), gives the evidence that the other two layers are healthy, scopes the damage to exactly one phase, and asks a question with two concrete answers rather than an open plea for help. A mentor can reply to it in one line.

Compare with "setup isn't working, I'm stuck" — which is the same situation, but costs a week because it takes three emails to establish what the lab above shows at a glance: four of the five capabilities were never in danger.

7 · Verification

Before you start step 1
  • I can state the order — Python and the repo, then Ollama, then Git — and give the reason in one sentence.
  • I know that --mock --sample runs the whole pipeline with no model and no data of my own, and I know why that matters.
  • I know that numbers from --mock or --sample never go into the write-up.
  • I can name the three layers an error can live in, and sort ModuleNotFoundError and Could not reach Ollama into the right ones.
  • I have set aside about an hour, and I know that roughly half of it is a download I should start early and not watch.
  • I know which single step breaks nothing today and is still not optional.
Going deeper (optional)

The pattern in this page has a name outside of setup: bisection. Faced with a system that fails and many possible causes, you do not test causes at random — you arrange things so that each test cuts the number of remaining candidates roughly in half. Adding one layer at a time is bisection applied in advance, before the bug exists.

You will use it again in three places on this project, and it is worth noticing each time: when the six code TODOs are done one at a time against a test suite rather than all at once; when a prompt change in Phase 4 is made alone so that the difference in the numbers can be attributed to it; and when a disagreement between two runs at temperature 0 is investigated by re-running a single item rather than the whole experiment. The tooling changes and the move does not.
