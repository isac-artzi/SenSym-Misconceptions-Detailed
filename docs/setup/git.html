Git, the small version

Five commands, one file of exclusions, and a way to name the exact state of the project that produced a number.

Git is enormous and you need almost none of it. This page teaches five commands and one habit, and deliberately refuses to teach branches, merges, rebases or pull requests — you are one person working on one project, and those exist to solve a problem you do not have. Budget forty minutes. What you get at the end is the ability to write, in Phase 5, "these numbers came from commit phase-4-complete", and have that sentence still be true in a year.

By the end of this page you can

  • Say what a commit is — a labelled snapshot of the whole project, not a saved file.
  • Run the five-command loop without looking it up: status, add, commit, push, pull.
  • Explain why python/data/ is committed and python/results/ is not, and defend that as a methodological choice rather than tidiness.
  • Write a commit message that says what changed and what it means.
  • Tag a milestone so a figure in your write-up can name the state that produced it.
  • Recognise the three things that will go wrong, and fix each without destroying work.
  • Say how much work you are risking at any moment, as a number.
I am on: Set this once. Every page on the site follows it.

1 · What a commit actually is

Saving a file writes one file to disk and forgets what was there before. A commit does something different: it records the state of every tracked file in the project at one instant, gives that state a name, attaches your message, your identity and the time, and keeps it forever. The name is a forty-character hexadecimal string like 6d9261d1f4…, and the first seven characters are usually enough to identify it.

Commit · a labelled snapshot of the whole project

A commit is not a saved file and not a backup of one folder. It is a photograph of python/misconception/, python/data/, python/tests/ and everything else that git is tracking, all at once, with a caption.

Because the photograph covers everything at once, the code and the data inside a single commit are guaranteed to be the versions that existed together. That guarantee is the entire reason this page exists.

Why a researcher cares is not mainly "so I don't lose my work". In Phase 5 you will write "recall for the misconception-aware condition was 0.72", and a reader is entitled to ask which forty responses, which labels, which prompt, which version of analyze.py? Without a history the honest answer is "the files as they were that afternoon, which have since changed". With one, the answer is a seven-character string that anybody can restore and rerun. "The numbers in my write-up" and "the code that produced them" become the same thing, permanently. That property is called reproducibility, and it is the difference between a result and an anecdote.

The failure this prevents is specific, and it is common

You run the experiment on a Tuesday and get recall 0.72. On Thursday you fix a labelling mistake in responses.csv — a genuine improvement. On Sunday you write up the 0.72. The number in your report was produced by data that no longer exists anywhere, and rerunning now gives 0.75. Neither number is wrong, but you can no longer say which one your report is about.

Nothing dishonest happened. That is what makes it dangerous.

How much are you risking right now?

The other reason to commit is duller and more immediate. The work sitting on your laptop and nowhere else is work you can lose, and the amount grows every hour you do not push. At roughly five hours a week on this project:

$$\text{hours you can lose} = 5 \times (\text{weeks since your last push})$$

Lab · what a gap in the history costs

Pick a way of working, then move the disaster. The green band is what is safely on GitHub; the red band is what only exists on your laptop and dies with it. Notice what happens to the red band when the disaster lands inside Phase 3.

The lesson of that picture is not "commit constantly out of fear". It is that the cost of a gap is not constant: three silent weeks during Phase 3 costs you something you cannot buy back with effort, and three silent weeks during Phase 2 costs you an irritating afternoon. Commit according to what is at stake.

3 · The loop

Five commands, always in this order, as many times a week as you sit down to work. Read the loop as a sentence: what did I change, which of it do I mean to keep, keep it with a reason, send it to GitHub — and pull first if anything might have changed there.

1 · git status — what have I changed?

Run this before anything and after everything. It is free, it changes nothing, and it is the only command here that can never hurt you.

$ git status
On branch main Changes not staged for commit: (use "git add <file>..." to update what will be committed) modified: python/data/responses.csv Untracked files: (use "git add <file>..." to include in what will be committed) python/data/EXAMPLES.md python/results/ no changes added to commit (use "git add" and/or "git commit -a")

Three categories, and telling them apart is most of understanding git. Modified means git already knows this file and it has changed since the last commit. Untracked means git has never seen this file and will not save it unless you say so. Anything listed under neither is identical to the last commit and needs no attention.

2 · git add — which of it do I mean to keep?

$ git add python/data/responses.csv python/data/EXAMPLES.md
On branch main Changes to be committed: (use "git restore --staged <file>..." to unstage) modified: python/data/responses.csv new file: python/data/EXAMPLES.md

Naming files one at a time is a small amount of extra typing that buys you the habit of looking at what you are about to save. git add . adds everything at once and is where accidental commits come from. Use the explicit form until it annoys you, and then use it anyway.

3 · git commit -m — keep it, with a reason

$ git commit -m "Add 40 labelled responses, 20 M / 20 C"
[main 6d9261d] Add 40 labelled responses, 20 M / 20 C 1 file changed, 2 insertions(+)

6d9261d is the snapshot's name. That string is what a report cites. Section 5 is entirely about what goes in the quotation marks.

4 · git push — send it to GitHub

$ git push
To https://github.com/isac-artzi/SenSym-misconception-aware-llm 183c457..6d9261d main -> main

A commit that has not been pushed does not exist off your laptop. The lab in section 1 measures exactly this: the red band is the work that is committed-but-not-pushed as well as the work that is not committed at all. Both die with the disk.

5 · git pull — bring down what changed there

$ git pull
Updating 183c457..8e12189 Fast-forward python/misconception/prompts.py | 6 +++--- 1 file changed, 3 insertions(+), 3 deletions(-)

Fast-forward is the word you want. It means your work and the incoming work did not overlap, so git simply moved you forward. Pull at the start of a session, not the end; pulling first is how you avoid the divergence in section 7.2.

The whole loop, as you will actually type it 
$ git pull
$ git status
$ git add python/data/responses.csv
$ git commit -m "Add R21-R28 for M06 and M07, four M and four C"
$ git push

Roughly ninety seconds. Do it at the end of every working session, and do it twice during a Phase 3 session, because Phase 3 is where the irreplaceable hours are.

4 · What goes into the history, and what does not

Some files belong in the permanent record and some do not, and the rule is not "big files out, small files in". The rule is a claim about your research:

The rule

Commit what cannot be regenerated. Exclude what can.

Your dataset — forty responses in python/data/responses.csv and ten misconception statements in python/data/misconceptions.csv — is the scientific contribution of this project. It exists because you wrote it, and no command brings it back. It goes in the history, and so does every version of it, so that "which labels produced this number" always has an answer.

Everything in python/results/ is a function of the data and the code: given the commit, analyze.py rebuilds all of it. Committing it stores a derived thing next to the thing it derives from, where the two can silently drift apart. And __pycache__/ is compiled bytecode Python writes for its own convenience — machine output, different on every machine, meaning nothing.

The exclusions live in .gitignore at the top of the repository. The lines that matter here:

__pycache__/ *.py[cod] .pytest_cache/ results/* !results/.gitkeep

A pattern ending in a slash matches a directory. A leading ! means "except this one" — .gitkeep is an empty file whose only job is to make git keep an otherwise-empty folder, because git tracks files and has no concept of an empty directory.

Where a pattern is anchored — this catches people, and it has caught this repository

Whether a pattern applies everywhere or only at the top depends on whether it contains a slash in the middle. __pycache__/ has none, so it matches at any depth. results/* does, so git anchors it to the folder holding the .gitignore — the repository root — and it therefore means /results/* only. But the outputs on this project are at python/results/, one level down. Do not take my word for which line is doing the work; ask git. observed

$ git check-ignore -v python/misconception/__pycache__/analyze.cpython-311.pyc
.gitignore:2:__pycache__/ python/misconception/__pycache__/analyze.cpython-311.pyc
$ git check-ignore -v python/results/metrics.csv
(no output, and the exit status is 1 — meaning: nothing ignores this file)

The fix is one word, and it is exercise 8.3. The habit is the real lesson: check-ignore -v tells you which line of which file made the decision, which beats guessing at a pattern language you use twice a year.

The one exception, and it is the whole point of the page

When you have the final run that your write-up quotes, commit its outputs on purpose. -f forces a file in past .gitignore:

$ cd python
$ git add -f results/metrics.csv results/predictions_baseline.csv results/predictions_misconception_aware.csv
$ git commit -m "Final run: llama3.2:3b, temp 0, 40 items, both conditions"

Now the numbers you quote and the per-item predictions behind them are in the same snapshot as the data and the code. Anyone can check your arithmetic without rerunning the model — which matters, because two runs at temperature 0 may still differ slightly, so "just rerun it" is not a complete answer.

5 · Commit messages for research

This is the part most git guides skip, and it is the part that pays you back. A message on a software team answers what changed. On a research project it has to answer what changed and what it means, because in Phase 5 you will read your own history as a lab notebook — a dated record of what you did and in what order — and "update data" tells you nothing about a decision you made eight weeks ago. Write in the imperative present, as if completing "this commit will…", and be specific with counts, identifiers and reasons.

Not usefulUsefulWhat the useful one buys you in Phase 5
update data Add 40 labelled responses, 20 M / 20 C You can see from the history alone that the dataset reached full size and was balanced by construction, and on what date. That balance is why the majority-class baseline is 50%.
fixed it Fix TODO 5c — recall was dividing by TP+FP instead of TP+FN Every number produced before this commit is wrong in a known way, and you can say exactly how. Without it you would have to rerun everything to find out whether it mattered.
final FINAL v2 Switch MODEL_NAME to llama3.2:1b; 3b swapped to disk on 8 GB A methods section writes itself: which model, and the honest reason for it. Six weeks later you will not remember that the reason was memory rather than accuracy.

Three rules that cover every case. Say the count — "40 responses", "R21–R28", "6 of 6 TODOs" — because a number is checkable and "some" is not. Say the reason when there was a choice, especially a choice you might be asked to defend at a check-in. Never write a message that would be true of a hundred other commits. If update would fit here, it fits everywhere, which means it identifies nothing.

Commit small, commit often

A commit that changes one thing can be described in one clause; a commit that changes six things gets "lots of stuff", because there is no honest short sentence for it. Message quality and commit size are the same problem. Small commits also undo cleanly: undoing "add eight responses" is a precise operation, and undoing "a week of work" is not an operation at all.

6 · Tagging a milestone

Commit names like 6d9261d are precise and unmemorable. A tag is a readable label you stick onto one commit, so you can refer to it by a name a human can type and a reader can look up.

Run these — but read the next box first 
$ cd path/to/SenSym-misconception-aware-llm
$ pytest -q
$ git tag phase-3-complete
$ git push --tags
To https://github.com/isac-artzi/SenSym-misconception-aware-llm * [new tag] phase-3-complete -> phase-3-complete

Note that git push and git push --tags are separate acts. Pushing commits does not push tags. A tag that exists only on your laptop labels nothing that anyone else can see, which defeats the purpose.

Only tag when pytest -q is green

Plainly: a tag is a promise that this state of the repository works. Run the tests first, every time, and tag only on a clean pass.

....... [100%] 7 passed in 0.42s

A tag on a broken commit is worse than no tag, because it is an assertion you did not check and someone will later rely on. If the tests fail, fix them and tag the fix.

Four tags are enough for the whole project: phase-2-complete when the six TODOs pass, phase-3-complete when the forty responses are written and locked, phase-4-complete on the real run, and phase-5-final on the state your write-up describes. Then Phase 5 can say, in the caption under a figure:

What this makes possible

"Figure 2 — confusion matrices for both conditions. Produced by python/misconception/analyze.py at tag phase-4-complete (6d9261d), model llama3.2:3b, temperature 0, n = 40."

Every claim in that caption is checkable by a stranger with the repository URL. Compare it with "Figure 2 — confusion matrices", which asks the reader to take your word. The whole of this page exists so that you can write the first caption.

7 · When it goes wrong

Symptom 7.1committed something I shouldn't have

You committed a file of private notes, a half-finished experiment, or something with a password in it.

Diagnosis and fix

Nothing is lost, ever, and there is no emergency. Which fix you want depends on one question: have you pushed it?

Not pushed yet. Undo the commit but keep the files exactly as they are on disk:

$ git reset --soft HEAD~1

HEAD~1 means "one commit before the current one". --soft moves the label back and touches nothing else, so every file is untouched and your changes are staged again. Unstage the file you did not want, then recommit:

$ git restore --staged notes.txt
$ git commit -m "Add R29-R32 for M08, two M and two C"

Already pushed. Do not rewrite the history — other copies exist. Add a new commit that undoes the old one:

$ git revert --no-edit 6d9261d
[main 8e12189] Revert "oops: committed my notes" 1 file changed, 1 deletion(-) delete mode 100644 notes.txt

Then git push. The file is gone from the current state and the record shows honestly that it was there and was removed — the correct outcome for a research log. To stop it coming back, add it to .gitignore and untrack it without deleting it from disk:

$ git rm --cached notes.txt

Two commands can actually destroy work, and neither is on this page: anything containing --force, and git reset --hard. If a page on the internet tells you to run either, stop and ask first. Every other git command is recoverable.

If what you committed was a real secret — a token, a password — treat it as published the moment it was pushed, because it is still in the history after a revert. Change the secret itself rather than trying to scrub the repository; rotating it takes two minutes and actually works.

Symptom 7.2branch has diverged

! [rejected] main -> main (fetch first), or fatal: Need to specify how to reconcile divergent branches.

Diagnosis and fix

You committed on your laptop; someone else — me, on this project — committed to GitHub; neither commit knows about the other. Git will not guess which order they belong in. The push is refused first:

! [rejected] main -> main (fetch first) error: failed to push some refs to 'https://github.com/isac-artzi/SenSym-misconception-aware-llm' hint: Updates were rejected because the remote contains work that you do not hint: have locally.

This is git protecting your work, not rejecting it. If it had accepted the push, the other commit would have been overwritten. Do what the hint says — pull, then push:

$ git pull --no-rebase
$ git push

On a fresh installation the first pull may stop and ask which style you want, with fatal: Need to specify how to reconcile divergent branches. Answer once, for this laptop, and you will not be asked again:

$ git config --global pull.rebase false

That chooses merge, which keeps both sets of work and both sets of commits. It is the right default for you: it never rewrites anything that already exists.

Usually the pull just prints Fast-forward and you push. Occasionally you both changed the same lines and you get:

CONFLICT (content): Merge conflict in python/data/responses.csv Automatic merge failed; fix conflicts and then commit the result.

Open the file. Git has marked the disputed region with <<<<<<<, ======= and >>>>>>>. Your version is above the =======, the incoming version below. Decide which is right — or write a third thing — delete all three marker lines, then git add that file and git commit. It looks far worse than it is. Ask me the first time.

The prevention costs nothing: git pull at the start of every session. A conflict is only possible in work that overlapped, and pulling first shrinks the overlap to whatever happened in the last hour.

Symptom 7.3asked for a password

git push asks for a username and password, and your real GitHub password is rejected.

Diagnosis and fix

Your password is not wrong. GitHub stopped accepting account passwords over git in 2021 and wants a personal access token instead — a long generated string that you can revoke without changing your password, and which can be limited to one repository. The error says so:

remote: Support for password authentication was removed on August 13, 2021. fatal: Authentication failed for 'https://github.com/isac-artzi/SenSym-misconception-aware-llm'

The easy fix, and the one to do: install GitHub's own command-line tool and let it handle this once.

$ gh auth login

Choose GitHub.com, then HTTPS, then Login with a web browser. It opens a page, you approve, and it stores a credential in the macOS Keychainin the Windows Credential Manager. You are never asked again on that laptop. Get gh from cli.github.com.

The manual fix, if you would rather not install anything: on GitHub, go to Settings → Developer settings → Personal access tokens → Fine-grained tokens, generate one with read and write access to this repository only, and paste it when git asks for a password. Copy it immediately — GitHub shows it exactly once.

A token is a password in every practical sense. Do not paste it into a file in the repository, do not send it in a message, and if you ever do either, delete the token on GitHub and make a new one. That takes thirty seconds and is the whole reason tokens exist rather than passwords.

You have just written eight new responses. git status says:

M python/data/responses.csv ?? python/data/notes-to-self.md ?? python/results/

Which commands do you run, in what order, and which of those three lines do you deliberately leave alone? Write the exact commands.

Exercise 8.2 ★★writing

Rewrite each of these as a message you would be glad to find in the history in Phase 5. Invent whatever plausible specifics you need.

(a) changes   (b) fix prompt   (c) results

Then say, in one sentence for each, what question your version answers that the original does not.

Solution

(a) Add R33-R40 for M09 and M10; dataset now complete at 40, 20 M / 20 C — answers when did the dataset become complete, and was it balanced? The balance is the fact that fixes the majority-class baseline at 50%, so it is worth having in the record rather than reconstructed later from the file.

(b) Make OUTPUT_FORMAT_INSTRUCTION blunter; 3b was returning prose instead of VERDICT: M — answers why is the prompt worded so repetitively? Nobody would guess that the answer is "because a small model ignored the polite version", and that observation is itself a finding about small-model reliability.

(c) Final run: llama3.2:3b, temp 0, 40 items, both conditions — answers which run is the one the write-up quotes? With several runs in the history this is the difference between a report you can defend and one you cannot.

The common shape: each rewrite contains at least one number or identifier, and each answers a question that will actually be asked. That is the whole test. If you cannot think of a question your message answers, the commit is probably doing too many things — split it.

Exercise 8.3 ★★code

Section 4 showed that results/* in .gitignore does not ignore python/results/metrics.csv, because a pattern with an interior slash is anchored to the folder holding the .gitignore.

Propose a one-line change that fixes it, then verify your fix with a command rather than by eye. What must you be careful not to break?

Solution

Change the two lines to name the real location:

python/results/* !python/results/.gitkeep

Verify, do not assume. From the repository root:

$ git check-ignore -v python/results/metrics.csv
.gitignore:27:python/results/* python/results/metrics.csv

It now names the line that made the decision. Check the exception survives too — this must print nothing, because .gitkeep is re-included and re-included files are not ignored:

$ git check-ignore -v python/results/.gitkeep

What you must not break: the ! line has to be updated in step with the pattern above it. A negation only works against a pattern that matched in the first place, so leaving !results/.gitkeep next to python/results/* would stop the folder being kept in the repository, and a fresh clone would arrive with no python/results/ at all — at which point analyze.py fails on a first run for a reason that looks nothing like its cause.

An alternative one-word fix is to write results/ with no interior slash at all, which matches a directory of that name at any depth. It is shorter, and it is worse: it would also silently ignore a results/ folder anywhere else in the project. Prefer the explicit path.

The transferable lesson is check-ignore -v. It converts "I think this is ignored" into "line 27 of .gitignore ignores this", and that difference is the same difference the rest of this page is about.

Exercise 8.4 ★★thinking

Set the lab to "commit at the end of every phase" and move the disaster across all twelve weeks. What is the worst loss, and in which week does it occur? Now explain why the answer argues for committing more often than once a phase, and say precisely where in the twelve weeks the extra commits are worth most.

Solution

Commits land at the ends of weeks 2, 4, 6, 9, 10 and 12. The gaps are 2, 2, 2, 3, 1 and 2 weeks. The worst case is the longest gap, so the maximum loss is a disaster at the end of week 8: the last push was week 6, three weeks earlier, giving $3 \times 5 = 15$ hours.

Why that argues for more commits. Two things coincide badly: the longest gap is Phase 3, and Phase 3 is the only phase whose output cannot be regenerated. Fifteen hours of Phase 2 is an annoying afternoon retyping code you understand. Fifteen hours of Phase 3 is roughly twenty-four hand-labelled responses that exist nowhere else, and a second attempt would produce different responses — not even the same dataset.

The extra commits are worth most in weeks 6 to 9. Committing after every batch of eight responses turns the maximum loss there from fifteen hours into about two, at ninety seconds a time. Nowhere else is the ratio that good.

Which is why "commit once a week" is the wrong rule and "commit when you have made something you would not want to make twice" is the right one — the same reproducible-or-not distinction that decides what goes in .gitignore.

Exercise 8.5 ★★research

Your Phase 5 report contains the sentence: "Recall for the misconception-aware condition was 0.72, against 0.55 for the baseline." Recall here is $\text{TP} / (\text{TP} + \text{FN})$ with M — "this response contains a misconception" — as the positive class.

List everything that must be true of your repository for a stranger to check that sentence a year from now. Which items on your list does git provide, and which does it not?

Solution

What must be true. (1) The forty responses and their ground-truth labels are in the history, in the exact version used. (2) The prompt text for both conditions is in that same commit — the two conditions differ only in the prompt, so the prompt is the independent variable and not a detail. (3) The scoring code that turned predictions into recall is in that commit, so its definition can be inspected rather than assumed. (4) The per-item predictions are recorded, so 0.72 can be recomputed by hand from a 2×2 table without running the model. (5) That commit is named in the report, by tag or by hash. (6) The model name and temperature are recorded. (7) The interval is reported: with n = 20 items in the positive class, 0.72 is roughly 14 of 20, and its Wilson 95% interval is wide, so a bare 0.72 overstates what you know. (8) The 0.55 is compared against the 50% majority-class floor, which is 50% here by construction because the dataset is 20 M and 20 C.

What git provides. Items 1 to 5 directly. The data, prompts and code are in the snapshot; the forced commit of results/predictions_*.csv from section 4 covers the per-item predictions; the tag from section 6 covers the naming. Item 6 is provided indirectly and only if MODEL_NAME and the temperature are in config.py rather than typed on a command line — which is one reason they live in a file.

What git does not provide. Items 7 and 8 are your judgement, not your tooling. Git will faithfully preserve a commit in which you reported 0.72 with no interval and no baseline, and the permanence makes that worse rather than better. Version control makes a claim checkable; it does not make it honest. The second is your job, and it is the harder one.

Exercise 8.6 ★★★research

You run the experiment on Monday and tag it phase-4-complete. On Tuesday you change nothing at all, rerun at temperature 0, and one item flips: recall moves from 0.72 to 0.70.

This is expected on this project and gets reported rather than hidden. Design the commits and tags you would make. What exactly does each one contain, what do the messages say, and what do you write in the report?

Solution

Do not move the tag. A tag that moves is worse than no tag: it means an earlier reader and a later reader can read the same label and see different states. phase-4-complete stays on Monday's commit forever.

Commit the second run alongside the first, not over it. Save Tuesday's outputs under distinct filenames so both survive in the same snapshot:

$ cd python
$ git add -f results/metrics_run2.csv results/predictions_baseline_run2.csv results/predictions_misconception_aware_run2.csv
$ git commit -m "Add run 2: identical config, R14 flipped M to C, recall 0.72 -> 0.70"
$ git push
$ git tag phase-4-run2
$ git push --tags

The message carries the finding, not just the file list: anyone reading the history knows a rerun happened, which item moved, and what it did to the headline metric, without opening a CSV. Identical filenames would be a mistake — overwriting metrics.csv hides the difference inside a diff nobody will read, and makes the working copy silently disagree with your report. Two runs are two observations; they should be two rows, not one row that changed.

What goes in the report. Something close to: "The pipeline was run twice at temperature 0 with identical configuration (phase-4-complete, phase-4-run2). One of forty items changed verdict between runs, moving recall for the misconception-aware condition from 0.72 to 0.70. Temperature 0 makes sampling greedy but does not make a run bit-identical, so a small amount of run-to-run variation is expected. The reported figures are from run 1; run 2 is in the repository."

Why this is a result and not an embarrassment. A 0.02 wobble in recall from a rerun is real information about how much precision a claim on forty items can carry. It sits naturally next to the Wilson interval, which is wide for the same underlying reason: n = 40 is small. A write-up that reports the wobble is more credible than one that quietly reports whichever run looked better — and git is what makes reporting it cost nothing, because both runs are already saved.

9 · Verification

Before the check-in
  • git --version prints a version, and git config --global user.name prints my name.
  • I can run the loop — status, add, commit, push — without looking it up.
  • The repository page on GitHub shows my commits, with messages I would be happy to read out.
  • Not one of my messages is update, fix, or a bare filename.
  • python/data/responses.csv is in the history; nothing in python/results/ is, except a final run added on purpose with -f.
  • git check-ignore -v tells me which line ignores a file, and I have run it at least once.
  • pytest -q passes, and only then did I run git tag and git push --tags.
  • I can say, out loud, what a commit is and why a tag makes a figure caption checkable.
Going deeper (optional)

Two commands worth knowing that are not part of the loop.

git log --oneline --decorate prints the history as a list, with tags shown against the commits they name. This is your lab notebook, and it is why section 5 matters:

6d9261d (HEAD -> main, tag: phase-3-complete) Add 40 labelled responses, 20 M / 20 C 2a606ee Fix TODO 5c — recall was dividing by TP+FP instead of TP+FN b6b338a Switch MODEL_NAME to llama3.2:1b; 3b swapped to disk on 8 GB

git diff shows what you have changed since the last commit, line by line, before you commit it. Read the diff, then commit; it catches the stray edit you made at eleven at night and forgot about. It also makes an AI coding assistant safe rather than corrosive: commit before you let it touch a file, and the diff shows you exactly what it did while one command undoes it. You cannot review a change you cannot see, and work you cannot review is work you cannot defend at a check-in.

Finally, every push runs this project's tests on a fresh machine via .github/workflows/ci.yml, and GitHub puts a tick or a cross next to your commit. A cross is information, not a telling-off — click it and find the first red line, usually a file you forgot to git add. A tick is the cheapest check that the commit you are about to tag works on a machine that is not yours.
