How to get unstuck

Twenty minutes, four layers, four runs, and a question worth answering.

Being stuck is the ordinary condition of research, not a sign that something has gone wrong with you. What separates a productive week from a wasted one is not how often you get stuck but what you do in the first twenty minutes. This page is the method: decide which layer the problem is in, halve the search space until only one thing can be to blame, read the error from the bottom, and — if none of that works within twenty minutes — ask a question that can be answered in one reply.

By the end of this page you can

  • State the twenty-minute rule and say why both halves of it matter.
  • Name the four layers a bug can live in, and the one command that tests each.
  • Isolate any failure in this project to a single cause using at most four runs.
  • Read a Python traceback from the bottom and point at the line that is yours.
  • Recognise the twelve errors this project actually produces, on sight.
  • Write a question that gets an answer in one reply instead of four.
  • Decide when a problem is not worth solving, and what to do instead.
I am on: Set this once. Every page on the site follows it.

1 · The twenty-minute rule

Try alone for twenty minutes. Then ask. That is the whole rule, and both halves of it are load-bearing.

Asking at minute one is a real cost, and not mainly to the person you ask. It costs you the thing the twenty minutes would have bought: the memory of having worked it out. A fix you were handed does not survive contact with the next bug, because you never learned the shape of the search. It also costs you the ability to say, out loud at a check-in, how your own project works — and you will be asked. The point of this project is not a confusion matrix. It is that you can defend every step of how the confusion matrix got there.

Grinding for three days is a much larger cost, and it is the one that actually happens. You have about five hours a week. Three days of stuck is not three days; it is most of a fortnight of your research time spent on a wrong column name that somebody else would have spotted in nine seconds. The dataset you write in Phase 3 is the part of this project that nobody else can do for you. An install error is not.

So the rule is a budget, not a virtue test. Twenty minutes is roughly long enough to run the four checks in section 2, try one bisection from section 3, and read the traceback properly — which is most of what a mentor would do anyway. If those produce nothing, the next twenty minutes will very likely produce nothing either, because you have run out of moves rather than out of patience. That is the moment to ask.

The twenty minutes have to be real

Twenty minutes of re-running the same command and hoping is not twenty minutes of debugging. It is one minute of debugging, repeated. The clock only counts time in which you did something different from the last thing: changed one input, read one more line of the error, checked one more layer.

Set an actual timer. Everyone underestimates how long they have been stuck, in both directions — five minutes of frustration feels like an hour, and an hour of interesting flailing feels like ten minutes.

2 · Which layer is it in?

This is the single most useful debugging move there is, and it is not a fix — it is a question you answer before fixing anything. Every problem in this project lives in exactly one of four layers:

LayerThe question it answersThe one command
(a) Your machine Does Python exist, and are the four packages installed? python3 misconception/check_setup.py
(b) The model / server Is Ollama alive, and is the model on disk? ollama list
(c) Your code Do the functions still do what they claim? pytest -q  (from the repo root)
(d) Your data Is the CSV the shape I think it is? python3 -c "import pandas as pd; d = pd.read_csv('data/responses.csv'); print(d.shape, d.columns.tolist())"

Four commands, under a minute, and afterwards you know which third of the problem to look at. The temptation is always to skip this and start editing the file you were last working in. Resist it: editing code to fix a stopped server is how an afternoon disappears.

The error text usually tells you the layer, if you read it

You mostly do not have to run anything, because the message already says which layer it came from. The trick is that error messages are written by the layer that failed, so they use that layer's vocabulary:

  • command not found: ollama — the shell is speaking. Nothing Python-shaped is involved yet. Machine.
  • Could not reach Ollama at http://localhost:11434/api/generate — an address and a knock that went unanswered. This string is raised by ask_llm() in llm_client.py and it is never caused by your code. Model / server.
  • KeyError: 'ground truth' — a Python object was asked for something it does not have. A name you typed. Your code.
  • ERROR: data/misconceptions.csv has no real rows yet. — the program ran perfectly and is telling you what it found in a file. Your data.

None of those four needed a diagnosis. They needed reading. The most common single mistake in debugging is not misreading the error; it is not reading it at all, because a wall of red text triggers a reflex to scroll past. Section 4 is about slowing that reflex down.

A fifth possibility, and it is common

Nothing is broken. The yellow TODO warning, the [TODO] lines in check_setup.py, the address already in use message, and the fact that both conditions come out identical under --mock are all deliberate, documented behaviour. Before assigning a layer, ask whether the program is failing or just talking to you. Red is not the same as broken, and neither is yellow.

3 · Bisection: four runs locate anything

The project has two switches you can flip independently. --mock replaces the real model with a fake one built out of keyword rules, so it is instant and needs nothing installed. --sample replaces your data with the twelve demo responses in python/data/sample/. Two switches, two positions each, so four possible runs — and the pattern of which ones pass tells you where the fault is without you guessing once.

The four runs, in this order 
$ cd python
$ python3 misconception/run_experiment.py --mock --sample   # 1: fake model, demo data
$ python3 misconception/run_experiment.py --mock            # 2: fake model, YOUR data
$ python3 misconception/run_experiment.py --sample          # 3: real model, demo data
$ python3 misconception/run_experiment.py                   # 4: the real thing
$ python3 misconception/analyze.py

Stop as soon as one fails. The first failure is the informative one; running the rest is only for confirming the pattern.

Start at run 1 because it is the cheapest thing that can possibly work: no model, no network, no data of yours, about a second. If run 1 fails, nothing downstream is worth looking at, because the failure cannot involve the model or your data — neither is present. That is the whole idea. Each run either takes half the possible causes off the table or leaves them all on it, and either answer is progress.

Lab · The bisection grid

Pick a failure pattern. The grid shows which of the four runs passed; the readout names the culprit and the next command. Notice that you never diagnose a single cell — you diagnose a row, a column, or a corner.

The formal version of this is worth naming, because it is the same idea everywhere. If a failure could have any one of $n$ causes and each test can rule out half of them, you need

$$\lceil \log_2 n \rceil \text{ tests, not } n$$

to find it. proved — each test halves the surviving candidate set, so after $k$ tests at most $n / 2^k$ candidates remain, and that drops below 1 exactly when $k \ge \log_2 n$. With $n = 8$ suspect steps in a pipeline that is 3 tests instead of 8; with $n = 1000$ commits it is 10 instead of 1000. Git has this built in as git bisect, which walks your history the same way to find the commit that broke something. Same move, different search space. Once you have the habit, you stop asking "what is wrong?" and start asking "what can I rule out with one run?", which is a much easier question and always has an answer.

4 · Reading a traceback

A Python traceback is not a wall of text. It is a list, printed in a specific order, and almost all of the useful information is in the last four lines. Read it from the bottom.

Here is a real one. It comes from writing "ground truth" with a space instead of "ground_truth" with an underscore while doing TODO 5a in analyze.py — which is the most likely single mistake on that TODO, because the column reads as two words in English.

Traceback (most recent call last): File ".../site-packages/pandas/core/indexes/base.py", line 3641, in get_loc return self._engine.get_loc(casted_key) File "pandas/_libs/index.pyx", line 168, in pandas._libs.index.IndexEngine.get_loc File "pandas/_libs/hashtable_class_helper.pxi", line 7668, in ...PyObjectHashTable.get_item KeyError: 'ground truth' The above exception was the direct cause of the following exception: Traceback (most recent call last): File "/Users/arshi/wrong-in-a-particular-way/python/misconception/analyze.py", line 269, in <module> main() File "/Users/arshi/wrong-in-a-particular-way/python/misconception/analyze.py", line 219, in main cm = compute_confusion(df) File "/Users/arshi/wrong-in-a-particular-way/python/misconception/analyze.py", line 67, in compute_confusion tp = len(scored[(scored["ground truth"] == M) & (scored["prediction"] == M)]) ~~~~~~^^^^^^^^^^^^^^^^ File ".../site-packages/pandas/core/frame.py", line 4378, in __getitem__ indexer = self.columns.get_loc(key) File ".../site-packages/pandas/core/indexes/base.py", line 3648, in get_loc raise KeyError(key) from err KeyError: 'ground truth'

That is genuinely what Python printed, with the long site-packages paths shortened and the repeated ^^^^ underlines removed so it fits. Nothing else was changed.

How to read it, in order

  1. Last line: what went wrong. KeyError: 'ground truth'. A KeyError means something was looked up by name and the name was not there. The name it wanted is printed in quotes. That is your search term, and it is the only thing worth pasting into a search engine.
  2. Now go up to the last file path that is yours. Ignore every line containing site-packages or _libs — that is pandas' own code, and pandas is not broken. The deepest line under misconception/ is the green pair above: analyze.py, line 67, in compute_confusion. That is where. Two facts, ten seconds, and you have not opened a file yet.
  3. The line under it is the code that failed, printed for you, with ~~~~~^^^^ pointing at the exact expression. Here it points at ["ground truth"]. The error and the arrow together have now told you the answer.
  4. Read upward only if you still need to. The frames above are the call chain: main() called compute_confusion(df), which is how you got here. Useful when the same function is called from three places and you need to know which call did it. Usually you do not need it.
  5. "The above exception was the direct cause of the following exception" means one error was re-raised as another. Read the lower block; the upper one is pandas' internal plumbing showing its work.

Then check what the column is actually called, rather than what you remember it being called. One line, and it answers the question outright:

$ python3 -c "import pandas as pd; print(pd.read_csv('results/predictions_baseline.csv').columns.tolist())"
['response_id', 'misconception_id', 'response_text', 'ground_truth', 'prediction', 'model_reason', 'raw_reply', 'condition']
Nine bugs in ten are "the data is not what I thought it was"

Which is why the fix above is a print, not an edit. Before changing any line, print the thing you are about to use: print(df.head()) after loading, print(prompt) before sending, print(len(df)) after filtering. It feels too simple to be a technique. It is the technique.

5 · The symptom index

Twelve things that actually go wrong on this project, with the real message each one prints. The tag on the right names the layer, so you can check your own diagnosis against it. The six Ollama-specific ones are not repeated here — command not found: ollama, Could not reach Ollama, address already in use, model not found, unbearable slowness, and a predictions column full of ? all live in section 7 of the Ollama page.

Symptom 5.1machine

ModuleNotFoundError: No module named 'pandas'

Diagnosis and fix

Python started fine, so Python is installed. It could not find a library. The layer is your machine, and the fix is one command:

$ pip install pandas requests matplotlib scikit-learn

Then rerun python3 misconception/check_setup.py, which tests all four imports and prints a line each. Note that the import name and the install name are not always the same word: you import sklearn but you pip install scikit-learn. check_setup.py keeps both spellings in a list precisely because that mismatch confuses everyone once.

If pip itself is not recognised, try python3 -m pip install pandas. That form works whenever Python works, because it asks Python to run its own package installer instead of relying on a separate program being on your PATH.

Symptom 5.2machine

zsh: command not found: pythonpython3 : The term 'python3' is not recognized as the name of a cmdlet, function, script file, or operable program.

Diagnosis and fix

Not a broken install. The two systems disagree about what the program is called.

On macOS, python with no 3 usually does not exist at all — it was removed so that nobody accidentally ran the long-obsolete Python 2. Always type python3 on this machine. Every command on this site is written that way.

On Windows, the installer from python.org creates python but often not python3. Drop the 3: python misconception/check_setup.py. Everything else on the site is identical.

If neither name works, Python genuinely is not installed or not on your PATH — see the Python setup page. A useful tell: python --version printing Python 2.7.x means you have found the wrong one, not that you are fine.

Worth internalising as a pattern: "this exact word is not recognised" is always the machine layer, and it is almost never solved by editing code.

Symptom 5.3data

ERROR: data/misconceptions.csv has no real rows yet. followed by -> Fill in your 10 chosen misconceptions ... or run with --sample

Diagnosis and fix

Nothing is broken. load_misconceptions() in run_experiment.py drops every row whose statement begins with < — the angle-bracket placeholders the template ships with — and then checks whether anything is left. On a fresh clone, nothing is.

Two correct responses, depending on where you are:

Before Phase 3: add --sample. That switches to the twelve demo responses in python/data/sample/ and the pipeline runs end to end in about a second.

During or after Phase 3: open the file and check that you replaced the placeholder text rather than adding rows underneath it. A row still reading <statement> is invisible to the loader by design.

This filter exists so that a half-filled file fails loudly instead of quietly running your experiment on template text and producing numbers that look real. An error that refuses to guess is doing you a favour.

Symptom 5.4data

ERROR: /path/to/python/results/predictions_baseline.csv not found. Run python misconception/run_experiment.py first.

Diagnosis and fix

analyze.py reads what run_experiment.py wrote. If the file is not there, the run either never happened, stopped early, or wrote somewhere else.

Check in this order. One: did the run actually finish? It prints Saved -> ...predictions_baseline.csv for each condition. If you never saw that line, the run did not get that far, and the real error is further up your terminal scrollback.

Two: are you in the right directory? The paths in config.py are worked out relative to the file itself, so they are correct wherever you launch from — but the error message prints the full path it wanted. Read it and compare with where you are.

Three: list what is actually there.

$ ls python/results/

The general shape here is worth keeping: a "file not found" error always tells you the exact path it wanted. Comparing that string to the output of ls answers the question completely, and it is faster than thinking.

Symptom 5.5your code

KeyError: 'ground truth' — or any other column name in quotes.

Diagnosis and fix

Worked through line by line in section 4. In summary: the last line names the key that was missing; the deepest traceback frame under misconception/ names the file and line that asked for it; the ~~~~^^^^ marker points at the exact expression.

The four column names this project uses in predictions files are response_id, ground_truth, prediction and raw_reply. All lowercase, all underscores. Print the real list rather than trusting memory:

$ python3 -c "import pandas as pd; print(pd.read_csv('results/predictions_baseline.csv').columns.tolist())"

A subtler version of the same bug: a trailing space in a header, so the column really is called 'ground_truth '. It looks identical in a spreadsheet. It is visible the moment you print the list, because Python shows you the quotes.

Symptom 5.6data

pandas.errors.ParserError: Error tokenizing data. C error: Expected 5 fields in line 3, saw 6

Diagnosis and fix

A CSV separates columns with commas, so a comma inside a value has to be protected by wrapping that value in double quotes. One row of responses.csv has an unquoted comma in the response text, so pandas counted six columns on a five-column file and refused to guess which split was intended.

The message names the line. Open the file in a plain text editor — not a spreadsheet, which will hide the quoting from you — and go to that line:

R02,M01,C,Length helps, but a long password of common words is guessable.,notes R02,M01,C,"Length helps, but a long password of common words is guessable.",notes

Your responses will be full of commas, because they are sentences. The reliable habit is to quote every response_text value, always, whether or not it currently contains a comma — then the file cannot break later when you edit the wording.

Saving from Excel or Numbers usually does the quoting for you. Editing the file by hand afterwards is where it gets undone.

Symptom 5.7data

ERROR: 3 row(s) have a ground_truth that isn't 'M' or 'C'. and First offender is response_id 'R14' with value 'm'

Diagnosis and fix

load_responses() checks every label against {config.LABEL_MISCONCEPTION, config.LABEL_CORRECT} before spending a minute of model time, and names the first offender so you do not have to search. The usual causes are a lowercase m, a trailing space ("M "), or a spreadsheet autocorrecting something.

Fix the labels; do not relax the check. A stray 'm' silently treated as M is a row that quietly stops being counted, and with n = 40 a single lost row moves recall by two and a half percentage points.

This is a good example of a check that exists because of what it protects: the run it prevents would have taken minutes and produced a confusion matrix that was wrong in a way nothing downstream would have flagged.

Symptom 5.8not an error

A block of yellow text at the end of a run: ⚠ 2 TODO(s) not done — the worked versions were used.

Diagnosis and fix

This is not an error and the run succeeded. It is todo.report() telling you which TODOs still fell back to the worked version in reference.py. The full message says so explicitly: "The numbers above are real, but they aren't YOUR code's numbers yet."

The design is deliberate. If unfinished TODOs crashed the program you could never run anything until they were all done, so you would never see the finished shape and could not tell "my code is wrong" apart from "my setup is wrong". If they came pre-filled you would learn nothing. So they run, and they announce themselves.

What to do: nothing, until you get to that TODO. When you have filled one in correctly, its line disappears from the block on the next run — which is a rather satisfying progress bar. When all six are gone you get ✓ Nothing fell back — this run was entirely your code. in green.

Learning to tell "the program is warning me" from "the program has failed" is worth more than any individual fix on this page. Colour is a hint, not a verdict.

Symptom 5.9your code

FAILED tests/test_pipeline.py::test_confusion_agrees_with_sklearn - assert (n...

Diagnosis and fix

A failing test is the most useful error you can get, because it hands you a worked example of the disagreement. Run it on its own with -q and read the middle:

> assert (tp, fp, fn, tn) == (cm["TP"], cm["FP"], cm["FN"], cm["TN"]) E assert (np.int64(7),..., np.int64(8)) == (7, 3, 2, 8) E At index 1 diff: np.int64(2) != 3

Read it as: scikit-learn says the second number is 2, your code says 3. The second slot in that tuple is FP. So your false positives and false negatives are swapped — the classic TODO 5 mistake, because the two conditions differ only in which of M and C goes where.

Go back to the definitions and read them as sentences rather than symbols: FN = truth is M and prediction is C, a misconception that was there and was missed. FP = truth is C and prediction is M, a false alarm on an answer that was fine. Then check that your line for each matches the sentence.

Note the test that did not catch this: test_confusion_counts_land_in_the_right_boxes uses data with one FN and one FP, so a swap leaves it passing. A test only catches a bug if the data can tell the two cases apart — a genuinely useful thing to have noticed about testing.

Symptom 5.10data

Either pandas.errors.EmptyDataError: No columns to parse from file, or a clean run printing TP=0 FP=0 FN=0 TN=0 and every metric 0.0.

Diagnosis and fix

Two different sizes of empty, and they fail differently.

A completely empty file (zero bytes) gives EmptyDataError: No columns to parse from file. pandas cannot even find a header row.

A header-only file is worse, because it does not crash. Every count is genuinely 0, compute_confusion()'s safety check passes (0 + 0 + 0 + 0 = 0 scored items, which is correct), and compute_metrics() returns 0.0 everywhere thanks to its if denominator else 0.0 guards. You get a chart of empty bars and no complaint at all.

Check the size before believing any zero:

$ python3 -c "import pandas as pd; print(len(pd.read_csv('results/predictions_baseline.csv')))"

Then rerun run_experiment.py. The usual cause is a run interrupted with Ctrl-C after the file was opened, or a run that failed on the first condition and left the second file from an older attempt.

Worth writing down as a rule: an all-zero result is a suspicious result. Real data almost never lands in exactly one box. If accuracy comes out as precisely 0.0 or 1.0, look at the file before you look at the model.

Symptom 5.11not an error

analyze.py finishes, says Saved -> .../comparison.png, and no chart window ever opens.

Diagnosis and fix

Working exactly as designed. The second line of analyze.py's matplotlib setup is matplotlib.use("Agg"), with the comment "save to file instead of opening a window". Agg is a backend that draws into a file and never touches your screen, which is what you want for a script you will run twenty times.

The charts are on disk. Open the folder:

$ open python/results/explorer python\results\

You should find comparison.png, confusion_matrices.png and metrics.csv. If the PNG files are there but stale, check their modification time — you may be looking at a chart from an earlier run and diagnosing a problem that no longer exists.

If they are genuinely missing, read further up: analyze.py prints one Saved -> line per file, so the last one it printed tells you where it stopped.

Symptom 5.12not an error

Both conditions produce byte-for-byte identical results, so the comparison chart shows two equal bars everywhere.

Diagnosis and fix

Check the top of the run for *** MOCK MODE — these numbers are FAKE. Never report them. ***. If it is there, this is expected and documented: ask_llm_mock() extracts the student response from the prompt and applies a keyword rule to it. It never looks at the rest of the prompt, so the misconception list has nothing to act on and both conditions come out identical.

That is the correct behaviour for a mock. Its job is to prove the plumbing works, not to simulate a result. There is no real model for the prompt to influence.

If you are not in mock mode and the two conditions still match exactly, that is a genuine finding rather than a bug: at temperature 0 on a 3B model, it is entirely possible that adding the misconception list changes nothing at all. Report it. "The catalogue made no measurable difference on n = 40" is a real answer to the research question, and with an interval this wide it is one you should have been prepared for. Before reporting it, confirm the two prompts really did differ by printing one of each — test_baseline_prompt_does_not_leak_the_misconception_list checks exactly that, so pytest -q settles it in two seconds.

6 · How to ask a question well

Twenty minutes are up. A good question is not a longer question; it is a question that contains the three things the answerer would otherwise have to ask you for. Miss one and you get a reply that is a request for it, and the round trip costs a day.

  1. The exact command you ran, and what you expected it to do. Not "I ran the experiment" — the literal line, including the flags, because --mock --sample and no flags are different programs.
  2. The complete error, copied and not retyped. Copied, because retyping silently corrects the typo that caused it. Complete, because the last line names the fault and the middle names the file, and people habitually send only the last line.
  3. What you already tried. This is the one that gets left out, and it is the one that saves the most time: it stops the answer being a suggestion you have already ruled out, and it shows the twenty minutes happened.
Four rounds of questions back
hi, the analysis isn't working,
it says KeyError. do you know
what's wrong?
An answer in one reply
RAN — and what I expected
  cd python
  python3 misconception/analyze.py
  expected: metrics.csv + two PNGs
  in python/results/

GOT — copied, not retyped
  File ".../misconception/analyze.py",
    line 67, in compute_confusion
    tp = len(scored[(scored[
      "ground truth"] == M) ...
  KeyError: 'ground truth'

ALREADY TRIED
  Reran run_experiment.py --mock
  --sample first; it saved both CSVs
  fine. Opened predictions_baseline
  .csv and the header does say
  ground_truth. Guessing my TODO 5a
  line has the name wrong but I
  can't see the difference.

The second one is answerable without a single follow-up: the command locates the stage, the traceback locates the line, and "already tried" rules out the two things anyone would have suggested first. It also takes about ninety seconds to write, most of which is copying. Notice too that writing it out is often enough on its own — laying the three parts side by side is how you spot that the file says ground_truth and your line says ground truth. That is worth knowing: a properly written question frequently answers itself, which is the cheapest possible outcome.

7 · When to stop and change plan

Some problems should not be solved. Recognising those is a separate skill from debugging and it is the one that protects the schedule. The signal is always the same shape: the cost of the fix has grown larger than the value of the thing being fixed. Three versions of it come up on this project.

A locked-down laptop where Ollama will not install. Do not spend a fortnight on this. Ollama is required for exactly one step: the single real run in Phase 4. Everything else — the six code TODOs, all forty responses, the whole analysis and the charts — runs under --mock and --sample with nothing installed. Build all of it, then borrow one machine for one afternoon. The table in section 8 of the Ollama page lists which phases need it, and the answer is one row out of six.

A dependency that will not install. Which one matters, so check before panicking. scikit-learn is used only for the cross-check, and analyze.py already handles its absence: it catches the ImportError and prints (scikit-learn not installed — skipping cross-check), then carries on and produces every number and both charts. You lose one safety net, which you note in your methods, and nothing else. matplotlib is imported at the top of the file, so without it analyze.py will not run at all — but the fallback there is Google Colab, which is free Python in a browser with all four packages already present. Upload the two predictions CSVs and you have your charts in ten minutes.

Every fix producing a new error. Three fixes deep, each one revealing something else broken, is not a debugging problem — it is a signal that the environment is wrong at a level you should not be repairing by hand. Stop, write down the chain of errors exactly as it happened, and switch to Colab or a different machine. The chain is worth keeping; it is often the fastest thing to diagnose from, and it belongs in your notes file.

The one that is hardest to see from the inside

The fourth signal is not technical. If you have spent two sessions on the same obstacle, the problem is very unlikely to still be the obstacle — it is that the plan has a step in it that does not need to be there. That is a conversation, not a fix, and it usually ends with the step being deleted rather than solved.

Falling behind is fine and expected. If you fall behind, do less, not worse. A careful twenty-item study you can defend completely beats a rushed forty-item one you cannot, and the smaller n gets reported with its wider interval, honestly, as a limitation.

Before the check-in
  • I set a timer at least once this week, and I know roughly how long I was stuck.
  • I can name the four layers and the one command that tests each.
  • I have run the bisection — at minimum, run 1 — before asking about any failure.
  • I can point at the file and line in a traceback without opening any file.
  • Every question I sent contained the command, the complete error, and what I tried.
  • I know which yellow and [TODO] messages are expected and are not errors.
  • Anything I gave up on is written down, with what I switched to instead.
Going deeper (optional)

The four-run grid in section 3 is bisection over two binary switches. Git generalises the same move over your whole history. If the pipeline worked on Tuesday and does not today, and there are twenty commits in between:

$ git bisect start
$ git bisect bad                  # today is broken
$ git bisect good HEAD~20         # Tuesday was fine

Git then checks out the commit halfway between, you test it, and you say git bisect good or git bisect bad. Five rounds later it names the exact commit that broke things, out of twenty. That is $\lceil \log_2 20 \rceil = 5$, the same arithmetic as before. Say git bisect reset when you are done.

You will probably not need this on a project this size. It is here because recognising the pattern is the point: any time you can cut the candidates in half with one test, do that instead of looking for the answer directly.
