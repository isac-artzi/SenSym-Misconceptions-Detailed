1 · Why nothing crashes

There is a real tension in a project set up for learning. If unfinished code crashes the program, you cannot run anything until everything is done, so you never see the shape of the finished thing, and you cannot tell my code is wrong apart from my install is wrong. But if the code comes pre-filled, you learn nothing by reading it.

This repository does both, through one small function. Every place where you have to write something has a worked version sitting behind it. Look at python/misconception/todo.py:

def pending(todo_id, value, fallback, *args, **kwargs):
    if value is not None:
        return value
    if todo_id not in _fired:
        _fired.append(todo_id)
    return fallback(*args, **kwargs)

That is the entire mechanism. Each TODO site in the code looks like a line you write, followed immediately by a call to pending. Here is the real pair from run_experiment.py:

prompt = None  # <-- FIX ME
prompt = todo.pending("TODO 4a", prompt, reference.build_prompt,
                      condition, item["response_text"], misconceptions)

If your line still says None, pending notes the identifier in a list called _fired and calls the worked version in python/misconception/reference.py instead. The run completes, the charts appear, and at the end todo.report() prints a yellow block naming exactly what was not yours. The moment you write something that is not None, your value is returned untouched and the identifier never enters the list.

The consequence worth internalising

An unfinished TODO can never crash this program. Not once, not in any combination. The fallback is always there and always returns something of the right type.

So if you see a traceback, it is not "I have not got there yet". It is a real bug — a typo, a wrong column name, a missing file — and it is worth reading properly rather than shrugging at. This is the whole reason the mechanism exists: it removes an entire category of ambiguous failure, so every failure that remains is informative.

2 · Mock mode, and the one-second loop

Do every part of this phase with the fake model and the demo data. The command is the one you have already run:

Run these, in this order, after every change 
$ cd python
$ python3 misconception/run_experiment.py --mock --sample
$ python3 misconception/analyze.py

And, from the repository root rather than from python/:

$ pytest -q

--mock swaps the real model for ask_llm_mock(), a keyword rule that answers instantly and needs nothing installed. --sample swaps your (still empty) data files for the twelve demo responses in python/data/sample/. Together they take about a second.

A real run is eighty calls to a three-billion-parameter model and takes minutes. A mock run takes one second. That difference is not convenience, it is a different way of working: at one second you change a line and look, change a line and look, twenty times in ten minutes. At five minutes you change three things at once because waiting is boring, and then you cannot tell which one fixed it.

Never debug your code and your model at the same time

If you run against Ollama while your own code is unfinished, every failure has two possible sources and you have to rule one out before you can think about the other. Mock mode removes one of them entirely. When your code is right in mock mode, and it then breaks against the real model, you have learned something specific and useful: the difference is the model.

Everything on this page — all six TODOs, both scripts, the tests, the charts — can be finished without Ollama ever being installed.

The fake model gives both conditions identical results. That is correct.

ask_llm_mock() ignores the prompt it is handed and looks only at the student response inside it, so baseline and misconception_aware come out exactly the same. There is no model for the prompt to influence. Seeing two identical rows in metrics.csv is evidence the plumbing works, not evidence the experiment failed.

Everything --mock and --sample produce is demo data. Not a single number from this page goes into your write-up.

3 · The eight markers, six of which the program can check

todo.py holds a dictionary called LOCATIONS with eight entries. Six of them have a matching pending() call somewhere in the code and can therefore fire. Two of them do not exist anywhere except in that dictionary, because what they ask for is a decision, not a value — and no program can check whether you made a decision. The phase title says six because six is what the machine counts.

TODO 5a–5d — analyze.py · compute_confusion()

What they ask. Four lines, one per box of the confusion matrix, counting rows of a dataframe. The dataframe is called scored and has already had the unparseable replies removed. Two constants are in scope at the top of the file: M is "M" and C is "C".

What the reference does. One function, reference.count(scored, truth_col, pred_col, truth_val, pred_val), covers all four by taking the two labels as arguments. It filters on both columns with & and returns the length. Your four lines are that same expression written out four times with the letters swapped around.

How you know it is right. Three independent signals, in order of strength: the four counts add up to len(scored) and the program does not exit; all four identifiers leave the warning block; and analyze.py prints scikit-learn cross-check: MATCH ✓.

The mistake that is very easy to make here

The four counts are about two columns. It is genuinely tempting to write the true-positive line as "the rows where the model said M":

tp = len(scored[scored["prediction"] == M])          # WRONG

That is not the true positives. That is every alarm the model raised, real or false — it is \(TP + FP\). The word true in "true positive" is not describing the model's confidence; it is describing whether the model's positive was correct, which is a fact about your label, not about the model. A count that never looks at ground_truth cannot possibly be a count of correctness.

The same trap sits in front of all four. Every one of the four lines must mention both ground_truth and prediction. If one of yours mentions only one column, it is wrong, whatever number it produces.

The safety net catches it, which is the nice part. Immediately after your four lines, compute_confusion() does this:

total = tp + fn + fp + tn
if total != len(scored):
    sys.exit(...)

Every scored row lands in exactly one of four boxes, so the four counts must sum to the number of scored rows. With the wrong true-positive line above, the demo data gives \(8 + 2 + 4 + 2 = 16\) against twelve scored items, and the program stops and tells you so. An error message that arrives four lines after the mistake is a gift; hunting a silently wrong recall three weeks later is not.

4 · Which box does this land in?

Before you write the four lines, do the four counts by hand once. Positive class is M, "this response contains a misconception", throughout — every metric on this site is measured against it:

$$\text{recall}=\frac{TP}{TP+FN},\qquad \text{precision}=\frac{TP}{TP+FP}$$

Recall asks: of the misconceptions that were really there, what fraction did the model catch. Precision asks: of the alarms it raised, what fraction were real. A false negative is a misconception the tutor stayed silent about, which is the error this project cares about most.

Lab · which cell does this land in

The twelve demo responses, with the label from python/data/sample/responses.csv and the verdict the fake model actually gave on the run above. For each one, pick the box it belongs in. The grid keeps score by cell, so if you are systematically confusing one pair you will see it. When all twelve are classified the grid is the confusion matrix analyze.py prints.

The pattern, once

Every one of the four lines is this shape, with two letters changed:

tp = len(scored[(scored["ground_truth"] == M) & (scored["prediction"] == M)])

The brackets around each comparison are not optional. In pandas & binds more tightly than ==, so without them Python tries to compute M & scored["prediction"] and raises a TypeError that reads as if it were about something else entirely. Use &, not and: the latter asks for the truth value of a whole column and raises ValueError: The truth value of a Series is ambiguous.

5 · What "verified" means here

Run this from the repository root, not from python/:

$ pytest -q
................... [100%] 19 passed in 3.7s

Nineteen tests at the time of writing observed. Three of them matter for this page. test_confusion_counts_land_in_the_right_boxes builds a six-row frame whose answer you can check in your head — two TP, one FN, one FP, two TN — and asserts compute_confusion agrees. test_unparseable_predictions_are_excluded_not_guessed feeds it a ? and checks that it is reported rather than quietly scored. And test_confusion_agrees_with_sklearn builds twenty rows and compares your four counts against sklearn.metrics.confusion_matrix.

Two independent implementations agreeing

That last test, and the MATCH ✓ line analyze.py prints, are the only sense in which anything here is "verified". Your four pandas expressions and scikit-learn's C implementation were written by different people at different times for different reasons. If they produce the same four integers on the same data, the probability that both are wrong in the same way is small.

Note the ordering convention, because it is a classic source of silent error. scikit-learn returns its matrix in the order [[TN, FP], [FN, TP]] when you pass labels=[C, M] — negative class first. The house convention on this site puts the positive class first. Same numbers, opposite reading order. Swapping them is a mistake nobody notices until precision and recall have been reported the wrong way round in a paper.

What pytest -q does not tell you

All nineteen tests pass on a completely untouched clone. They have to: the tests call compute_confusion(), which falls back to reference.count(), which is correct. A green test suite proves the pipeline is correct. It does not prove any of it is yours.

The green fallback line is the only thing that proves authorship, and it is printed by the two scripts, not by pytest. Run both. Get both lines.

What you are aiming at, from a fresh run of each script:

✓ Nothing fell back — this run was entirely your code.

And what a partly finished run looks like, so you recognise it:

──────────────────────────────────────────────────────────── ⚠ 2 TODO(s) not done — the worked versions were used. The numbers above are real, but they aren't YOUR code's numbers yet. ──────────────────────────────────────────────────────────── TODO 4a misconception/run_experiment.py · run_condition() → build the prompt with build_prompt(...) TODO 4b misconception/run_experiment.py · run_condition() → send the prompt with ask(...)

One thing that message gets wrong: it ends by pointing at docs/03_TODO_CHECKLIST.md, and the paths inside that file still say src/. The repository moved to python/misconception/ and the checklist did not follow. Trust the code, then this site, then the checklist, in that order — and if you have five minutes, fixing those paths is a genuinely useful first pull request.

6 · Exercises

Exercise 6.1 ★by hand

Six items. Your label first, the model's verdict second: (M, M), (M, C), (C, C), (M, M), (C, M), (C, C).

Fill in TP, FN, FP and TN, then compute recall and precision as fractions before you convert them to decimals.

Solution

Take them one at a time. (M, M) is truth M and prediction M, so TP. (M, C) is a misconception the model called correct, so FN. (C, C) is TN. (M, M) is another TP. (C, M) is a false alarm on a correct answer, so FP. (C, C) is another TN.

TP = 2, FN = 1, FP = 1, TN = 2. They sum to 6, which is the number of items, so no row has been double-counted or dropped.

Recall = 2/(2+1) = 2/3 ≈ 0.667. Precision = 2/(2+1) = 2/3 ≈ 0.667. They happen to be equal here because FN and FP happen to be equal; that is a coincidence of this tiny example, not a general fact, and the very next exercise breaks it.

These are exactly the numbers in test_confusion_counts_land_in_the_right_boxes in python/tests/test_pipeline.py. That test was built the same way you just did it: work the answer out by hand where the answer is obvious, then check the code agrees.

Exercise 6.2 ★★code

Write the pandas expression that counts the false negatives in the dataframe scored, exactly as it would appear on the tp = ... FIX ME line in compute_confusion(). M and C are already in scope. Then say, in one sentence, why the C is where it is.

Solution
fn = len(scored[(scored["ground_truth"] == M) & (scored["prediction"] == C)])

A false negative is a response that really does contain a misconception — so ground_truth is M — which the model called correct, so prediction is C. The C is on the prediction side because it is the model that was wrong, not your label.

Two things to check before you move on. The comparisons are each parenthesised, because & has higher precedence than == in Python and the unbracketed version raises a TypeError. And it is &, not and; and would ask for the truth value of an entire Series and raise ValueError: The truth value of a Series is ambiguous.

An equivalent form you will see in other people's code, and which is worth recognising:

fn = int(((scored["ground_truth"] == M) & (scored["prediction"] == C)).sum())

A boolean Series summed counts its True values. Same answer; use whichever you can read faster at midnight.

This is the count that goes on the bottom of the recall fraction, and recall is the headline metric of this study, so of the four this is the one to get right first.

Exercise 6.3 ★★code

Write both TODO 4 lines as they should appear in run_condition(). Then explain why using ask matters rather than importing ask_llm and calling that.

Solution
prompt = build_prompt(condition, item["response_text"], misconceptions)
raw_reply = ask(prompt)

build_prompt is imported at the top of run_experiment.py from prompts, and its signature is build_prompt(condition, response_text, misconception_list). All three arguments are already to hand: condition and misconceptions are parameters of run_condition(), and item is the current row of the responses frame, whose text column is response_text.

Leave the todo.pending(...) lines underneath alone. Once prompt is no longer None, pending returns it unchanged and never calls the reference — the line becomes a no-op, and deleting it is optional tidying, not part of the task.

On the second line: ask is set four lines above the loop to ask_llm_mock when --mock was passed and ask_llm otherwise. Calling ask_llm directly would give code that is correct in every way except that --mock silently stops working, and you would be waiting on Ollama while believing you were in mock mode. Indirection like this — one variable that decides which implementation the rest of the function talks to — is worth recognising, because you will meet it constantly and it is nearly always there to make testing possible.

Exercise 6.4 ★★thinking

Suppose you write tp = len(scored[scored["prediction"] == M]) and get the other three lines right. Run against the demo data, where the fake model produces TP 4, FN 2, FP 4, TN 2 over twelve scored items. What number does that line produce, what does the program do, and what exactly does the message tell you?

Solution

The line counts every row where the model said M, regardless of your label. On this data that is the four real catches plus the four false alarms: 8. It is \(TP + FP\), the number of alarms raised, which is the denominator of precision, not the numerator.

Then the sanity check runs: \(8 + 2 + 4 + 2 = 16\), but len(scored) is 12, so compute_confusion() calls sys.exit and prints that your four counts add up to 16 against 12 scored items, with the suggestion to check that you used & and not |.

What the message tells you precisely is that some row was counted twice — the four false positives now appear in both tp and fp. What it does not tell you is which line is at fault; four counts and one sum is not enough information to localise the error. That is what the drill in section 4 is for.

Notice what would have happened without the check: recall would have been \(8/(8+2) = 0.8\) instead of \(4/(4+2) \approx 0.667\), a number that is wrong, plausible, and flattering. Cheap invariants that catch flattering errors are the most valuable kind.

Exercise 6.5 ★★code

Write a single pandas expression that produces all four counts at once from scored, and read TP and FN out of it. Then give one reason not to use it in compute_confusion().

Solution
ct = pd.crosstab(scored["ground_truth"], scored["prediction"])
tp = ct.loc[M, M]
fn = ct.loc[M, C]

On the demo predictions this prints:

prediction C M ground_truth C 2 4 M 2 4

Rows are truth, columns are prediction, and the labels are sorted alphabetically, so C comes before M in both directions. Reading TP off that table means reading the bottom-right cell, which is not where the site's convention puts it.

And that is the reason not to use it here. If the model never says M on some condition, the M column does not exist at all and ct.loc[M, M] raises a KeyError — crosstab only creates columns for values it actually saw. The four explicit counts return 0 in that case, which is the right answer. A "clever" one-liner that is correct on typical data and explodes on the edge case is a bad trade in analysis code, where the edge case is often the interesting result.

Once your four lines are written and cross-checked, using the library version is fine and normal. Writing it out by hand once is what earns you the right to trust the one-liner.

Exercise 6.6 ★★★thinking

On a completely untouched clone, pytest -q reports nineteen passes. Explain why, in terms of what todo.pending() does. Then answer the harder half: is that a flaw in the test suite? If you think it is, describe a test that would fail on a fresh clone and pass when the six markers are done, and say what that test would cost.

Solution

Why it passes. The tests import analyze and call compute_confusion(). Inside it, tp and the rest are still None, so each todo.pending() call records the identifier in _fired and returns reference.count(...), which is correct. The tests are testing the reference implementation and cannot tell the difference. The same is true of test_full_pipeline_runs_on_a_fresh_clone, which is exactly the point of that test: it exists to prove that a clone runs end to end before any work has been done.

Is it a flaw? No, because the tests and the fallback report answer two different questions. The tests ask is this pipeline correct. The report asks whose code is it. Both questions are worth asking, and no single signal answers both. A green suite plus a yellow warning block is a perfectly coherent state that means "everything works, none of it is yours yet" — and being able to read that state is the skill.

A test that would tell them apart. Something like:

def test_no_reference_fallbacks_remain():
    todo.reset()
    analyze.compute_confusion(_frame([("M", "M"), ("C", "C")]))
    assert not todo.any_pending(), sorted(todo._fired)

It would fail on a fresh clone with a message naming the unfinished markers, and pass once the four lines are written. todo.reset() and any_pending() already exist and the existing tests already use them.

What it costs. A red test suite from the first minute of the project. A beginner cannot then use "all tests pass" as a baseline meaning "my environment is sane", which is the single most useful thing a test suite gives someone who has just installed Python — and the reason the failure is surfaced as a yellow report at the end of a successful run rather than as a test failure. That is a deliberate trade, not an oversight. Being able to argue both sides of it is the answer; there is no single right one.
