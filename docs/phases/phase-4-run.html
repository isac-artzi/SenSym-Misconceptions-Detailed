Wrong in a Particular Way · Phase 4
The projectWin: a result you can describe exactly

The real run, twice

Eighty calls to the model, about a quarter of an hour of waiting, and a written record that makes the numbers mean something.

This is the shortest phase of the project and almost none of it is work. You type one command and watch a row of dots. What this page is really about is the ten minutes of writing you do while it runs, because a number without the conditions that produced it is not a result — it is a rumour. Budget one afternoon, and expect to run it twice.

By the end of this phase you can

  • State every condition that must hold before the run starts, and check each one.
  • Predict exactly how many calls the run makes and roughly how long it will take.
  • Read the progress output, and say precisely what a dot and an X each mean.
  • Write a provenance record complete enough that a stranger could repeat your run.
  • Say why "I used llama3.2" is not a specification of anything.
  • Run it a second time and decide, with a stated rule, whether a difference is reportable or noise.
  • Explain why parse_verdict() returns ? instead of guessing, and report the count without embarrassment.

1 · The pre-flight checklist

Every item here is cheap to check now and expensive to discover afterwards. A run started with the wrong dataset produces perfectly plausible numbers, and nothing in the output will tell you.

All seven must be true before you type the command
  • The six TODOs are yours. A mock run ends with the green line ✓ Nothing fell back — this run was entirely your code, not a yellow block. If a worked version is still standing in for your code, the run is not measuring what you wrote.
  • The dataset is finished, committed and tagged. Forty rows, twenty M and twenty C, a second reader's agreement figure written down, and the whole thing at tag phase-3-complete. The dataset is now frozen: editing an item after you have seen a result is how honest people produce dishonest work.
  • check_setup.py shows no [FIX] and no [TODO]. Both Ollama lines say [OK] and both data files report 40 and 10 real rows. This is the first point in the project where a [TODO] on a data file is genuinely a problem.
  • MODEL_NAME matches ollama list exactly. Character for character, colon included.
  • The laptop is plugged in, and will not sleep. Ten to twenty minutes at full processor load flattens a battery quickly, and a machine that sleeps mid-run kills the Python process. Change the sleep setting for the afternoon, then change it back.
  • The browser is closed. Not minimised — closed. Chrome and a language model compete for exactly the same memory, and if the model stops fitting, the run does not get slightly slower, it gets several times slower.
  • Your notebook is open at a blank page. Section 3 is what goes on it, and it gets filled in while the run is happening, not from memory afterwards.
Run these, in this order 
$ cd python
$ pytest ../ -q
$ python3 misconception/check_setup.py
$ python3 misconception/run_experiment.py
$ python3 misconception/analyze.py

Note what is not there: no --mock and no --sample. Those two flags have carried you through every earlier phase, and this is the one run where both must be absent. Any number produced with either flag is demo data and can never appear in your write-up.

2 · What the run actually does

The structure is two loops, and it is worth being able to state it without looking: for each condition, for each response, build the prompt, ask the model, write down what it said. So the number of calls is

$$\text{calls} \;=\; n_{\text{items}} \times n_{\text{conditions}} \;=\; 40 \times 2 \;=\; 80.$$

Eighty is the whole cost of this study. Each call is one HTTP POST to localhost:11434, and the two conditions are identical in every respect except the prompt text — same forty items, same model, same temperature, same order. That is what makes the comparison mean anything, and it is the reason the run is one command rather than two.

Here is what the terminal shows. Read it before you see it, so that nothing in it surprises you at the moment when a surprise would make you stop the run.

Using model: llama3.2:3b at temperature 0.0 Loaded 40 answers (20 misconception, 20 correct) Loaded 10 misconceptions --- Condition: baseline --- ..X.X......X..X..X...XX...X..X...X..X.X. Done in 341.2s (8.5s per item) Saved -> /Users/arshi/SenSym-misconception-aware-llm/python/results/predictions_baseline.csv --- Condition: misconception_aware --- ..X....X...X....X..X....X...X.X...X..X.. Done in 352.8s (8.8s per item) Saved -> /Users/arshi/SenSym-misconception-aware-llm/python/results/predictions_misconception_aware.csv ✓ Nothing fell back — this run was entirely your code. All conditions complete. Next step: python misconception/analyze.py
What a dot and an X actually mean

One line of run_experiment.py produces them:

mark = "." if verdict == item["ground_truth"] else "X"

A dot means the verdict parsed out of the model's reply was the same letter as the label you wrote in responses.csv. It does not mean the model was right in any deeper sense — your label is the standard here, and it is only as good as Phase 3 made it. It also does not tell you which letter: a dot on an M item and a dot on a C item look identical.

An X means the two letters differed, and it covers two quite different events: the model gave a clear verdict you disagree with, or the reply could not be read at all and came back as ?, which is never equal to M or C. You cannot tell those apart from the terminal. That is what section 5 is about.

The marks exist so you can see the run has not frozen. Do not try to count them as they appear, and do not start forming a conclusion at item twelve.

Expect somewhere between five and twenty minutes for the whole thing, on a laptop where the model fits comfortably in memory. observed That is a range from ordinary experience rather than a measurement on a controlled benchmark, and the first call is always slower than the rest because the model has to be loaded into memory. If a single item takes more than 120 seconds the client gives up and raises an error, which is TIMEOUT_SECONDS in config.py doing its job.

Lab · what a run costs, and what a bigger one would cost

Your study is the dot at 40 items and 2 conditions. Move the sliders to see what the scaled-up version costs: more items, or a third condition such as a second model. Below the amber line is a run you can sit through in one go; above it you are committing an evening, and above the red line you have to plan around it. The point of this lab is that run time is exactly linear in both sliders, so the whole budget is one multiplication.

3 · Recording the provenance

This is the part of the page that matters, and it is the part that feels like it does not.

A result is not a number. A result is a number plus the conditions that produced it. Detached from those conditions, "recall was 0.72" is an assertion nobody — including you in three months — can check, repeat, or argue with. The conditions are cheap to write down while they are in front of you and effectively impossible to reconstruct afterwards, because the things you would need are exactly the things that change: model files get re-pulled, config files get edited, laptops get replaced.

This is not a specification

"I used llama3.2."

llama3.2 names a family, not a model. It ships in at least a 1B and a 3B size, which differ by a factor of three in the amount of computation per answer and are visibly different in quality. Even llama3.2:3b alone is a moving target: a tag is a pointer, and the same tag can be re-pointed at different weights, which is why ollama list prints an ID alongside the name. And a model name says nothing about temperature, so it does not tell a reader whether your run was repeatable at all.

This is a specification:

"llama3.2:3b, ID a80c4f17acd5, temperature 0, commit 4f2a1b9, 14 August 2026, MacBook Air M2."

Six facts, each checkable by a stranger. The commit is the one people forget and the one doing the most work: the two conditions differ only in the prompt, so the prompt text is the independent variable of this entire experiment, and the only place the exact prompt text lives is that commit.

Collect the four things you cannot reconstruct

$ ollama list
$ ollama --version
$ git rev-parse --short HEAD
$ git status --short
NAME ID SIZE MODIFIED llama3.2:3b a80c4f17acd5 2.0 GB 3 weeks ago ollama version is 0.3.12 4f2a1b9

git rev-parse --short HEAD prints the name of the commit you are standing on — seven characters that identify one exact state of every file in the project. git status --short printing nothing is the important part: it means there are no uncommitted edits, so the commit hash you just wrote down really does describe the code that is about to run. If it prints anything at all, commit before you run, or the hash in your record is a lie.

The template

Copy this into your notebook and fill it in as the run happens. Do it twice, once per run.

RUN RECORD — misconception-aware LLM pilot
  run number ...... 1 of 2
  date, time ...... 2026-08-14, 21:40 local
  machine ......... MacBook Air M2, 8 GB RAM, macOS 15.5
  model name ...... llama3.2:3b            (ollama list, NAME column)
  model ID ........ a80c4f17acd5           (ollama list, ID column)
  ollama version .. 0.3.12                 (ollama --version)
  temperature ..... 0.0                    (config.py, TEMPERATURE)
  max tokens ...... 200                    (config.py, MAX_TOKENS)
  conditions ...... baseline, misconception_aware
  dataset ......... 40 responses (20 M, 20 C), 10 misconceptions
  commit .......... 4f2a1b9                (git rev-parse --short HEAD)
  tag ............. phase-3-complete
  working tree .... clean                  (git status --short printed nothing)
  elapsed ......... baseline 341.2 s, misconception_aware 352.8 s
  unparseable ..... baseline 3, aware 1    (analyze.py, "unparseable:")
  anything odd .... first call took ~25 s while the model loaded

Fifteen lines, four minutes, and it turns a folder of CSV files into a result. The last line is not padding: "anything odd" is where you write the thing you would otherwise mention to nobody and remember at the worst possible moment — that the browser was open for the first ten items, that the machine went to sleep once, that you noticed the model repeating itself.

Why by hand, when a script could do it

It could, and larger projects do exactly that: a run script that stamps the model, the commit and the timestamp into the output file automatically. That is the better engineering and it is a genuinely good extension to attempt in Phase 5.

The reason to write it by hand first is that the discipline is the point, not the file. Writing "temperature 0.0" out yourself is what makes you notice, later, when somebody's result does not say. Automating a habit you have never practised produces a field in a file that nobody reads and nobody checks.

4 · Run it twice

When the first run finishes and analyze.py has printed its numbers, do the whole thing again. Same command, same data, same everything. Write a second run record.

The reasoning is short. Temperature 0 means the model is supposed to take the most likely next word every time rather than sampling, so the same prompt should produce the same reply. A second run is the cheapest possible test of whether that is actually true on your machine, and it costs a quarter of an hour of doing nothing. If the two runs agree exactly, you have earned the right to write "the run was repeated and reproduced identically", which is a sentence very little student work can honestly include.

And if they do not agree, that is also a finding, and it gets reported rather than hidden. Temperature 0 makes the sampling greedy; it does not make the arithmetic bit-identical. Floating-point operations on a GPU are executed in an order that can vary between runs, and addition on floating-point numbers is not associative, so two mathematically identical computations can differ in the last few digits — which occasionally flips a verdict that was nearly a tie. observed The honest response is to report both runs and the number of items that moved. Deleting the second run because it disagreed with the first is the single most tempting piece of misconduct available to you on this project, and it is worth naming it now so you recognise the temptation when it arrives.

The rule, stated before you have any numbers

Zero items move. Say so in the methods: the run was repeated and reproduced exactly.

One or two items move (up to 5 percentage points). Expected. Report the headline numbers from run 1, and give run 2 one sentence in the methods with the count of items that changed.

Three items move (7.5 points). Borderline. Run it a third time before you write anything, and report the range across all three.

Four or more items move (10 points or more). Stop. This is not run-to-run variation, it is a difference in the conditions, and you have not found it yet. Do not average the runs, do not pick one — go and ask.

Deciding this rule now, before you have seen either set of numbers, is what makes it a rule rather than a rationalisation.

Lab · is the difference real, or is it the instrument?

Set run 1's score, then slide the number of items whose verdict changed in run 2 — drawn in the worst case, where every change moves the same way. The bars are 95% Wilson intervals; the shaded band is run 1's interval, which is the precision the study has at all. Notice how many items have to move before the difference is even visible against that band — and then read the last paragraph of the readout, which explains why the rule above is much stricter than the band.

The two questions in that last paragraph are worth separating carefully, because they get confused constantly. The Wilson interval answers how precisely do I know this model's accuracy on cybersecurity responses in general, and on forty items the answer is "not very" — about 27 points wide in the middle of the range. The rerun answers did my machine do the same thing twice on these exact items, and the answer should be "yes, or very nearly", because nothing about the situation changed. A rerun that moves ten points has not revealed uncertainty in your estimate. It has revealed that your two runs were not the same experiment.

What the methods section ends up saying

"The pipeline was run twice with identical configuration (llama3.2:3b, ID a80c4f17acd5, temperature 0, commit 4f2a1b9), on 14 and 15 August 2026. One of the forty items changed verdict between runs under the baseline prompt, moving baseline accuracy from 28/40 to 27/40. Reported figures are from run 1; run 2 is committed in the repository at tag phase-4-run2."

Three sentences. They tell a reader what you did, what varied, which numbers are the ones in the table, and where to check. Nothing in them is impressive, and that is the point: provenance is not meant to be impressive, it is meant to be sufficient.

5 · The question marks

parse_verdict() in llm_client.py has to turn a paragraph of model prose into one letter. It tries four things in order: the format the prompt asked for (VERDICT: M), then a bare M or C standing alone as a word, then a keyword sniff for "misconception" or "correct", and then it gives up and returns ?.

Giving up is a design decision, not a gap. The alternative — defaulting an unreadable reply to C — would be catastrophic in a specific and quiet way. Twenty of your items are C, so a silent default to C would convert every unreadable reply on a C item into a free true negative, inflating your accuracy and your specificity with answers the model never actually gave. Your numbers would get better precisely because the model got worse. A design that rewards you for the model's failures is a design that will eventually fool you.

What happens to the question marks downstream

compute_confusion() in analyze.py splits the rows in two:

unparseable = len(df[~df["prediction"].isin([M, C])])
scored      = df[df["prediction"].isin([M, C])]

The four boxes of the confusion matrix are counted over scored only, so if five replies were unreadable, every metric has a denominator of 35 rather than 40. The count is carried separately and printed on its own:

TP=13 FP=7 FN=5 TN=10 (unparseable: 5)

So whenever you quote a metric from a run with unparseable replies, quote the denominator with it. "Accuracy 0.66" and "accuracy 0.66 over the 35 items that produced a readable verdict, with 5 of 40 unreadable" are different claims, and only the second one is true.

Then report the count. "The 3B model produced unparseable output on 12.5% of items under the baseline prompt and 2.5% under the misconception-aware prompt" is a genuine, quotable finding about small-model reliability — arguably a more useful one for a school considering this technology than the accuracy figures, because it is about whether the thing can be relied on to answer the question it was asked. It is not an embarrassment and it is not a sign you did something wrong.

A low count is not proof that the parsing was clean

Strategies 2 and 3 are guesses with good manners. The keyword sniff returns M whenever the word "misconception" appears without the exact phrase "no misconception" — so a reply reading "this is not a misconception" is scored M, the opposite of what the model said. observed (Read the function and check that for yourself; it is four lines.)

So do not treat the unparseable count as the whole story. Open results/predictions_baseline.csv and read the raw_reply column for ten or fifteen items, especially the ones marked X. Ten minutes of reading raw replies tells you more about what the model is actually doing than any metric on the page.

6 · If it dies partway

The machine sleeps, Ollama falls over, you close the lid, the timeout fires on item 33. Whatever the cause, the situation is far less serious than it feels.

Nothing is lost that a rerun will not fix. The cost of the entire run is ten to twenty minutes of a laptop being warm, and the inputs — your forty items, your prompts, your code — are all sitting untouched in git exactly as they were. There is no partial state to repair.

Look at what is on disk. run_experiment.py writes a condition's CSV only after that condition's loop has finished, so you will find either a complete predictions_baseline.csv or no file at all, never a half-written one. If the crash came during the second condition, you have a complete baseline file and no aware file, and analyze.py will stop with ERROR: ... predictions_misconception_aware.csv not found rather than analysing half a study.

Do not try to resume from the middle

The temptation is to keep the complete baseline file and rerun only the condition that died. Do not. Two reasons, and the second is the important one.

It saves eight minutes. That is the entire prize, and it is not worth any amount of cleverness.

It costs you the sentence. After a resume you can no longer write "both conditions were run in a single execution with identical configuration" — you would have to write "the baseline condition was run at 21:40 and the misconception-aware condition at 23:15, after a crash of unknown cause, with the machine in an unknown state in between." A result you cannot describe in one clean sentence is a result you will spend the whole write-up apologising for. Fix the cause, delete the orphaned CSV, and start the whole thing again from the top with a fresh run record.

The one thing worth doing before you rerun is diagnosing the cause, because an unexplained crash usually repeats. A LLM ERROR mentioning Could not reach Ollama means the server stopped — check the menu bar. One mentioning the 120-second timeout means the model is not fitting in memory, and the fix is to close things or drop to llama3.2:1b and record the change of model in your run record. A Python traceback about a CSV is a data problem and belongs back in Phase 3.

7 · Exercises

Exercise 4.1 ★arithmetic

(a) How many calls does the full run make, and how many progress marks will you see? (b) The run prints Done in 341.2s (8.5s per item) for baseline and Done in 352.8s (8.8s per item) for the aware condition. What was the total time, and what would a third condition cost? (c) A dot appears for item 7. State precisely what that tells you and two things it does not.

Solution

(a) Forty items under each of two conditions, so $40 \times 2 = 80$ calls. You see 80 marks, in two runs of 40, each preceded by its --- Condition: ... --- header. One mark per call, always.

(b) $341.2 + 352.8 = 694.0$ seconds, which is 11 minutes 34 seconds, plus a few seconds for loading the CSV files and writing the results. A third condition at the same rate costs about $(341.2+352.8)/2 \approx 347$ seconds, roughly 5.8 minutes, taking the total to about 17.4 minutes. The per-item figures are just the elapsed time divided by 40: $341.2/40 = 8.53$, printed as 8.5.

(c) A dot means one thing only: the letter parsed out of the model's reply equalled the letter in your ground_truth column for that item. It does not tell you which letter — a dot on an M item and a dot on a C item look identical, so you cannot tell a caught misconception from a correctly ignored good answer, and therefore cannot compute recall from the marks. It also does not tell you the reply was well formatted: a verdict rescued by the keyword fallback prints exactly the same dot as a clean VERDICT: M. The marks are a liveness indicator, not data; the data is in the CSV.

Exercise 4.2 ★★arithmetic

You run the study twice. Under the misconception-aware prompt, run 1 scores 29 of 40 and run 2 scores 27 of 40. Compute the 95% Wilson interval for each, decide whether the difference is reportable as a change in performance, and write the sentence that goes in your methods.

The Wilson interval for $k$ successes in $n$ trials, with $\hat p = k/n$ and $z = 1.96$:

$$\frac{\hat p + \dfrac{z^2}{2n} \;\pm\; z\sqrt{\dfrac{\hat p(1-\hat p)}{n} + \dfrac{z^2}{4n^2}}} {1 + \dfrac{z^2}{n}}.$$
Solution

The pieces that do not depend on $k$. With $n = 40$ and $z^2 = 3.8416$: the denominator is $1 + 3.8416/40 = 1.09604$; the centre shift is $z^2/(2n) = 0.04802$; and the constant inside the square root is $z^2/(4n^2) = 3.8416/6400 = 0.00060$.

Run 1, 29/40. $\hat p = 0.725$. $\hat p(1-\hat p)/n = (0.725)(0.275)/40 = 0.00498$, so the root is $\sqrt{0.00498 + 0.00060} = \sqrt{0.00558} = 0.07473$ and the half-width term is $1.96 \times 0.07473 = 0.14647$. The centre is $0.725 + 0.04802 = 0.77302$. So

$$\text{lo} = \frac{0.77302 - 0.14647}{1.09604} = 0.5716, \qquad \text{hi} = \frac{0.77302 + 0.14647}{1.09604} = 0.8389,$$

giving 72.5%, 95% CI [57.2%, 83.9%].

Run 2, 27/40. $\hat p = 0.675$. $(0.675)(0.325)/40 = 0.00548$; $\sqrt{0.00548 + 0.00060} = 0.07800$; $1.96 \times 0.07800 = 0.15289$; centre $0.675 + 0.04802 = 0.72302$. So $\text{lo} = (0.72302 - 0.15289)/1.09604 = 0.5202$ and $\text{hi} = (0.72302 + 0.15289)/1.09604 = 0.7992$, giving 67.5%, 95% CI [52.0%, 79.9%].

Is it reportable as a change? No, on two separate grounds. The operational rule from section 4 fires first: two items moved, which is 5.0 percentage points, inside the expected wobble. And the intervals make the same point from the other direction — they overlap across almost their whole length, and run 2's estimate of 67.5% sits comfortably inside run 1's interval of [57.2%, 83.9%]. There is no version of this data in which a two-item difference is a finding.

The sentence. "The run was repeated with identical configuration. Two of the forty items changed verdict under the misconception-aware prompt between runs, moving accuracy from 29/40 to 27/40. Reported figures are from run 1." Note what it does not say: it does not say the model "got worse", because two items on forty is not evidence of anything getting worse.

Exercise 4.4 ★★thinking

Run 1 scores 30 of 40. You rerun it the next morning, changing nothing you are aware of, and get 18 of 40. The 95% Wilson intervals are [59.8%, 85.8%] and [30.7%, 60.2%].

(a) Do the intervals overlap, and does that settle the question? (b) List what you would check, in order of likelihood. (c) Why is averaging the two runs the wrong move?

Solution

(a) They overlap, but only just: run 1's lower limit is 59.8% and run 2's upper limit is 60.2%, an overlap of 0.4 of a percentage point. And no, that does not settle anything — it is the wrong test for this question. The Wilson interval describes uncertainty about the model's accuracy on responses like yours in general. Here the two runs used the identical forty items, so sampling uncertainty is not in play at all. Twelve items out of forty changing verdict between two runs of the same code on the same data is a 30-point move, three times the "stop and ask" threshold, and it is a fault, not noise.

(b) In order of likelihood:

1. A different model answered. Run ollama list and compare the ID against your run record — if you re-pulled, or an update re-pointed the tag, the name can match while the weights do not. Also check MODEL_NAME in config.py, and check you did not fall back to llama3.2:1b after a timeout.

2. A file changed. Run git status --short and git diff. An edited prompt, an edited item, an edited temperature. This is exactly the failure the "working tree clean" line in the run record exists to catch.

3. The flags differed. Check your shell history for --mock or --sample on one of the two runs. Twelve items is a very plausible gap between the real model and the keyword-based fake one.

4. The temperature was not 0. Confirm the run's own first line said at temperature 0.0. At a nonzero temperature the model samples rather than taking the most likely token, and a swing of this size is entirely ordinary.

5. Parsing collapsed. Compare the unparseable counts. If run 2 had ten more question marks, the drop is a formatting failure rather than a reasoning failure — a different story with a different fix, and one you would misreport badly if you had not looked.

(c) Averaging assumes the two runs are two noisy measurements of the same quantity. That is the assumption in question. If one run used a different model or different prompt text, the average is a number describing no experiment that was ever performed, and quoting it would be worse than quoting either run alone. Averaging discards the single most informative thing you have — that they disagreed — and replaces it with a plausible-looking number that hides the problem. Find the cause, fix it, run twice again, and write down what the cause was.

Exercise 4.5 ★★arithmetic

analyze.py prints this for the baseline condition on your forty items:

TP=13 FP=7 FN=5 TN=10 (unparseable: 5)

(a) How many items were scored, and how do you know the counts are consistent? (b) Compute accuracy, precision and recall, with M as the positive class, and state each denominator. (c) What is the widest and narrowest accuracy over all forty items consistent with this output? (d) The aware condition has 1 unparseable rather than 5. What does that do to your comparison?

Solution

(a) $13 + 7 + 5 + 10 = 35$ scored items, and $35 + 5 = 40$, so the unparseable count and the four boxes account for every row. compute_confusion() checks this itself and exits if the four counts do not add up to len(scored). You can also check the split by class: the truly-M items are $TP + FN = 13 + 5 = 18$, and the truly-C items are $FP + TN = 7 + 10 = 17$, so of your 20 M and 20 C items, 2 M and 3 C came back unreadable.

(b) With M — "this response contains a misconception" — as the positive class:

$$\text{recall} = \frac{TP}{TP+FN}, \qquad \text{precision} = \frac{TP}{TP+FP}, \qquad \text{accuracy} = \frac{TP+TN}{TP+FN+FP+TN}.$$

Accuracy $= (13+10)/35 = 23/35 = 0.657$, over 35 scored items. Precision $= 13/(13+7) = 13/20 = 0.650$, over the 20 items it called M. Recall $= 13/(13+5) = 13/18 = 0.722$, over the 18 truly-M items that produced a readable verdict — not over all 20. Three different denominators in three consecutive numbers, which is exactly why a metric quoted without one is not a claim.

(c) The five unreadable replies could in principle have been anything. If every one of them would have been wrong, accuracy over forty items is $23/40 = 0.575$; if every one would have been right, it is $28/40 = 0.700$. So the true accuracy on your forty items lies somewhere in $[0.575,\ 0.700]$, a band 12.5 points wide, and the reported 0.657 sits inside it. Quoting that bound is a strong, honest move: it says exactly how much the unreadable replies could be costing you, without pretending to know.

(d) It means the two conditions are scored over different numbers of items — 35 against 39 — so they are not quite like-for-like, and you must say so rather than quietly comparing two fractions with different denominators. It is also a result in its own right, and possibly a more interesting one than the accuracies: the misconception-aware prompt is longer and more explicit about the output format, and it produced readable output five times more reliably. "The catalogue prompt improved format compliance from 87.5% to 97.5% of items" is a sentence worth having, and it is invisible to anyone who treats question marks as an embarrassment to be minimised.

Exercise 4.6 ★★★code

Read parse_verdict() in python/misconception/llm_client.py. (a) Construct a reply that the function scores as M even though the model plainly said the opposite, and trace it through all four strategies. (b) You discover this after the run, and fixing it would change your results. What is the honest procedure? (c) Why is that procedure a rule about timing rather than a rule about code?

Solution

(a) The reply "This is not a misconception." The function uppercases the text first, then:

Strategy 1 looks for VERDICT: M or VERDICT: C. There is no VERDICT, so no match. Strategy 2 looks for a standalone M or C as a whole word — \b([MC])\b. The only single-letter word here is "A", so no match. Strategy 3 asks whether "MISCONCEPTION" appears while "NO MISCONCEPTION" does not. The text contains "NOT A MISCONCEPTION", which contains "MISCONCEPTION" but not the literal string "NO MISCONCEPTION", so the test passes and the function returns M. Strategy 4 is never reached. The model said C and the pipeline recorded M.

If that reply came on a truly-M item it prints a dot and lands in TP, and you would never look at it again. That is the more dangerous of the two cases.

(b) Four steps, in this order. Measure it before you touch anything: open the predictions CSVs and count how many rows have a raw_reply with no VERDICT: line — those are the rows the fallbacks decided, and if the number is zero the bug is real but did not fire and nothing needs rerunning. Record the decision in your run record and your write-up: what you found, when you found it, and what you did. If you change the parser, rerun both conditions from scratch — never one, because a comparison between a condition parsed the old way and a condition parsed the new way is meaningless. Report both sets of numbers, pre-fix and post-fix, and say which you are headlining and why. Nothing here is hidden and nothing is deleted.

(c) Because the code change is fine and the temptation is not. Improving a parser is ordinary good practice on any other day. What makes it dangerous today is that you now know which direction the change moves your numbers, so a decision you would have made on the merits becomes a decision you might make on the outcome — and neither you nor a reader can tell those two apart from the finished result. The protection is the freeze: the dataset, the prompts and the parser are fixed before the run, and any change after it is made in public, with both sets of numbers on the page. This is the same principle as not editing items after seeing a score in Phase 3, and it will be the same principle again when you are choosing which metric to headline in Phase 5. Every one of them is a rule about when you are allowed to decide, not about what you are allowed to decide.

Going deeper (optional)

Why temperature 0 is not the same as determinism. Temperature 0 fixes the selection rule — always take the highest-scoring next token — but it does not fix the arithmetic that produces the scores. Those are floating-point sums computed in parallel, and floating-point addition is not associative, so a different order of summation can change the last few bits of a score. Almost always that changes nothing. Occasionally two candidate tokens are close enough that it flips which one wins, and one flipped token early in a reply can change the whole verdict. observed This is worth understanding rather than memorising, because it is the reason the honest sentence is "we repeated the run and one item moved" rather than "temperature 0 guarantees reproducibility".

A third run is cheap. Nothing about the design stops at two. If the first two disagree at all, a third costs a quarter of an hour and turns "they differed" into "the score across three runs was 29, 27, 29 of 40", which is a much more informative sentence and takes no more space in the write-up.

What a bigger version of this study would record. Serious work stamps the provenance into the output automatically: model name and digest, commit hash, timestamp, library versions, random seeds and hardware, written into the results file by the run script itself. If you want an extension in Phase 5, add six lines to run_experiment.py that write those into a results/run_meta.csv. Do it after you have kept the record by hand twice, so you know what belongs in it.
